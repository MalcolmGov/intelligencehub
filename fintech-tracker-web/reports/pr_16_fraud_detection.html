Executive Summary

PayGuard Fraud Shield is a real-time transaction monitoring system designed to detect fraudulent transactions, money laundering patterns, and sanctions violations in South African fintech operations. The platform combines rule-based scoring with machine learning to identify suspicious activities across millions of daily transactions from mobile money providers like MTN MoMo.

Business Value

Prevents financial crime losses (estimated R2.1B annually in SA fintech fraud)
Enables FICA/AML regulatory compliance and SAR filing automation
Real-time alert generation for fraud analysts (sub-second latency)
Fraud ring detection via graph analytics — identifies coordinated attack patterns
POPIA/PCI-DSS compliance for data protection and card handling

Technical Architecture

System Components

1. Transaction Ingestion

Kafka Topic: transactions.inbound (25k msg/sec)

Receives real-time transaction events from payment gateways, mobile money providers. Schema: {txn_id, amount, sender_id, receiver_id, timestamp, device_id, location, merchant_category}

2. Risk Scoring Engine

Service: fraud-risk-engine (Python FastAPI)

26 composable rules: velocity, amount anomaly, geolocation jump, device fingerprinting, behavioral patterns. Produces risk_score (0-100).

3. Graph Fraud Ring Detection

Service: fraud_ring_detector.py (Neo4j)

Detects coordinated fraud rings via graph traversal. Models: sender→receiver relationships, shared devices, shared IPs, shared locations.

4. Device Binding Service

Repo: device-binding/src/index.ts (TypeScript)

Fingerprints devices (OS, browser, hardware identifiers) to detect multi-account abuse, SIM swap fraud.

5. Signal API

Repo: api/src/index.ts (TypeScript REST)

Public API for risk assessment, device lookup, sanctions screening. Rate-limited (1k req/sec).

6. Analyst Dashboard

Repo: frontend/src (React)

Real-time fraud alerts, transaction investigation, case management, rule performance analytics.

Data Flow Architecture

Transaction Event ↓ [Kafka: transactions.inbound] — 25k msg/sec, 3-day retention ↓ [Risk Scoring Engine] — FastAPI, 26 rules (velocity, amount, geolocation, device, behavior) ↓ [Neo4j Graph] — fraud_ring_detector.py detects coordinated patterns ↓ [Alert Generation] — Kafka: fraud.alerts (high/medium/low severity) ↓ [Cache: Redis] — Device fingerprints, user risk profiles (5min TTL) ↓ [Persistent Store: PostgreSQL] — Transaction history, audit logs, case records ↓ [React Dashboard] — Real-time WebSocket updates for analyst review

Security & Compliance (Critical for Fintech)

POPIA (Protection of Personal Information Act) — South Africa

  • Data Minimization: Collect only necessary PII (sender name, phone, but not full ID). Implement data retention policies (delete transaction details after 90 days if not flagged).
  • Consent: Ensure customers consent to fraud monitoring. Document in T&Cs.
  • Data Residency: All transaction data must reside in South African data centers (POPIA requirement). Use on-prem or AWS/Azure ZA regions only.
  • Breach Notification: If PII is compromised, notify affected individuals within 72 hours and POPIA Regulator.
  • Third-Party Processing: DPA required for any cloud provider or data processor.

FICA (Financial Intelligence Centre Act) — South Africa

  • AML/CTF Reporting: File Suspicious Activity Reports (SARs) within 24 hours of detection to SARS. Implement SAR generation in case management system.
  • Sanctions Screening: Screen all transactions against OFAC, UN, SARB watchlists (Rule 022). Mandatory — non-compliance = criminal liability.
  • Audit Trail: Maintain audit logs of all rule decisions, analyst actions, SAR filings. Immutable (write-once database).
  • KYC Requirements: Validate customer identity and beneficial ownership for high-risk transactions.

PCI-DSS Level 1 (Payment Card Industry)

  • Card Data Encryption: AES-256 encryption at rest, TLS 1.2+ in transit. Key management (AWS KMS / HashiCorp Vault).
  • Network Segmentation: Card data isolated in separate VLAN/security group. No cross-traffic to non-payment systems.
  • Quarterly Vulnerability Scans: External pen testing by approved vendors (e.g., Trustwave, Qualys).
  • Annual Audit: SOC 2 Type II attestation or PCI-DSS audit report required.

SARB Guidance Note 4 of 2017 (Cyber Resilience)

  • Incident Response Plan: Document response procedures for fraud ring detection, system compromise, data breach.
  • Business Continuity: RTO <4 hours, RPO <1 hour. Tested failover to secondary data center.
  • Access Controls: MFA for all admin/analyst accounts. Audit logs of access (who accessed what, when).
  • Risk Assessment: Annual cyber risk assessment. Remediate critical findings within 30 days.

Implementation Guidelines

Phase 1: ML Model Training & Deployment (Weeks 1-4)

Week 1: Data Preparation
Export 12 months historical transaction data + fraud labels from PostgreSQL. Feature engineering: amount, velocity, geolocation, device, behavioral features. Split: 80% train, 10% val, 10% test.
Week 2: Model Training
Train XGBoost and Isolation Forest models. Hyperparameter tuning via GridSearchCV. Evaluate: AUC-ROC, precision, recall, F1. Target: AUC >0.90.
Week 3: Explainability & Validation
Add SHAP values for model interpretability (required for FICA audit trail). Validate on holdout test set. Document decision rationale for compliance.
Week 4: Integration & Testing
Replace ai_fraud_rules.py stub with trained models. Load models into risk engine. Integration test: end-to-end transaction → risk score. Stress test at 10k req/sec.

Phase 2: AML/Sanctions Integration (Weeks 5-6)

Week 5: Watchlist Integration
Integrate OFAC API (daily refresh). Implement local PostgreSQL cache (sanctions_watchlist table). Create Rule 022 sanctions screening handler. Test: known sanctioned names must trigger alert.
Week 6: SAR Filing Automation
Implement SAR (Suspicious Activity Report) auto-generation in case management. Schema: {txn_id, risk_score, rules_triggered, analyst_notes, sar_filed_date}. Test SFTP upload to SARS secure server.

Phase 3: Anomaly Detection (Weeks 7-9)

Week 7: Statistical Models
Implement Z-score and IQR-based anomaly detection for transaction amounts. Per-customer baseline calculation (running mean/stddev). Flag transactions >3σ from baseline.
Week 8: Autoencoder (Optional Advanced)
Train sparse autoencoder on normal transaction patterns. Reconstruction error → anomaly score. Complements ML model for pattern discovery.
Week 9: Integration & Tuning
Add anomaly scores to risk engine. Tune thresholds to balance detection vs. false positives. Backtest on historical data.

Phase 4: Load Testing & Optimization (Weeks 10-11)

Week 10: Production Volume Testing
Load test Kafka pipeline at 2M txns/day (25k msg/sec). Monitor: CPU, memory, latency. Identify bottlenecks. Risk engine: test 10k req/sec. Neo4j: graph query performance under load.
Week 11: Optimization & Failover
Optimize slow queries. Add database indices. Implement circuit breakers for downstream dependencies. Test failover: Kafka broker loss, DB failure, Neo4j unavailability. Verify RTO <4 hours.

Phase 5: Case Management & Human-in-the-Loop (Weeks 12-13)

Week 12: Workflow Automation
Build case management system: create case on high-risk alert, assign to analyst, track investigation status (open/investigating/resolved/false_positive). Implement SAR filing workflow.
Week 13: Feedback Loop
Analyst feedback → training labels. Implement label upload, store in PostgreSQL. Use for monthly model retraining. Measure improvement (AUC, coverage).

Phase 6: Production Hardening & Compliance (Weeks 14-15)

Week 14: Security & Compliance Audit
PCI-DSS assessment: card data encryption, network segmentation, access logs. POPIA audit: data minimization, residency, consent. FICA audit: SAR workflow, sanctions screening, audit trail. Document all controls.
Week 15: Deployment & Runbooks
Deploy to production Kubernetes cluster. Document runbooks: incident response, model retraining, watchlist updates, SAR filing. Train fraud analysts on dashboard and case management.
