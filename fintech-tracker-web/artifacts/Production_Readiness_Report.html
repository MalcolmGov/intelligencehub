🔧 Azure DevOps Configuration
Effort: Medium · 2–3 days
🔴
Install Microsoft Security DevOps Extension
Install the MSDO marketplace extension in your Azure DevOps organisation. Required for SAST scanning in Stage 2. One-click from the Azure DevOps Marketplace.
BLOCKER
🔴
Create 4 Service Connections
One service connection per environment: sc-dev, sc-uat, sc-preprod, sc-prod. Each must be an Azure Resource Manager connection scoped to the respective resource group. Set up under Project Settings → Service Connections.
BLOCKER
🔴
Create Variable Groups with Secrets
Create variable groups in Azure DevOps Pipelines → Library and populate: ACR_NAME, ACR_LOGIN_SERVER, IMAGE_REPO, LOG_ANALYTICS_WORKSPACE_ID, APPINSIGHTS_INSTRUMENTATIONKEY (×4 environments), AZURE_SUBSCRIPTION_ID, AZURE_OPENAI_ENDPOINT, AZURE_OPENAI_KEY.
BLOCKER
🔴
Configure Pipeline Environments with Approval Gates
Create four Environments (Dev, UAT, Pre-Prod, Prod) under Pipelines → Environments. Add manual approval checks to UAT, Pre-Prod and Prod. Assign named approvers to each gate. Set 7-day timeout for UAT/Pre-Prod, 24-hour for Prod.
BLOCKER
🟡
Configure Agent Pools
Verify ubuntu-latest is available in your organisation, or update vmImageName in azure-pipelines.yml to match your hosted or self-hosted pool name.
HIGH
🟡
Commit Pipeline Files to Repository
Commit the azure-pipelines.yml and all templates/, scripts/, and infra/ folders to the root of your Azure DevOps repository. Configure the pipeline to use this YAML file under Pipelines → New Pipeline.

Effort: High (if not done) · 1–4 weeks
🔴
Containerise the Application (Dockerfile)
The pipeline expects a Dockerfile at the repository root. If the application is not yet containerised, this is the single highest-effort prerequisite. The multi-stage Dockerfile should produce a minimal runtime image from the .NET SDK build.
BLOCKER
🔴
Create Helm Charts
The deploy-stage.yml template calls helm upgrade. Helm charts (Chart.yaml, values.yaml, templates/) need to be authored for the application, with per-environment values files (values-dev.yaml, values-uat.yaml, values-preprod.yaml, values-prod.yaml).
BLOCKER
🟡
Update Test Selector Heuristics
The intelligent-test-selector.py script uses a source→test heuristic that assumes test classes are named after source classes (e.g. PaymentService → PaymentServiceTests). Update the mapping logic to match your actual test project structure if it differs.

The smoke test steps in the deploy template call a /health endpoint on the deployed application. Ensure your application exposes a health check endpoint that returns HTTP 200 when the app is ready.

🗓️ Recommended Implementation Phases

Phase 1 — Foundation & Dev Pipeline
Week 1
Commit all pipeline files to the Azure DevOps repository
Deploy Bicep infrastructure to Azure subscription
Create service connections and variable groups
Install Microsoft Security DevOps marketplace extension
Configure Dev Environment (no approval gate)
Trigger first pipeline run: Build → Security → Deploy Dev → Test Dev
Outcome: Working Build + Security + Dev deployment pipeline delivering real security scan results and AI-selected tests on every commit.
Phase 2 — UAT & Pre-Prod Promotion
Week 2
Configure UAT and Pre-Prod Environments with approval gates and approver groups
Create sc-uat and sc-preprod service connections
Provision Azure Container Apps environments for UAT and Pre-Prod
Enable Stages 5–8 in the pipeline (UAT + Pre-Prod)
Validate alert emails and App Insights connectivity
Outcome: Full Dev → UAT → Pre-Prod pipeline with manual approvals, blue/green deployments, and dynamic monitoring alerts active.
Phase 3 — Production Go-Live
Week 3
Configure Prod Environment with senior engineer approval gate
Create sc-prod service connection
Verify anomaly detection script with real Pre-Prod metrics
Review anomaly scores from Phase 2 runs and tune threshold if needed
Enable Stages 9–10 (Deploy Prod + Monitor Prod)
Run team walkthrough and document rollback runbook
Outcome: Full 10-stage pipeline live. AI anomaly detection active in Production with automatic rollback capability.
Phase 4 — Tuning & Optimisation
Weeks 4–6
Calibrate anomaly detection threshold based on real production traffic patterns
Refine intelligent test selector heuristics based on missed test coverage
Add Teams webhook to Action Groups for alert notifications
Review SARIF reports and tune SAST severity thresholds
Establish performance baselines after 3+ successful production deployments
Outcome: Stable, calibrated pipeline with low false-positive rate on anomaly detection and reliable test selection.

⚠️ Key Risks

Risk Likelihood Impact Mitigation
Application not yet containerised Medium High Assess containerisation effort upfront. This is the single largest unknown — address in pre-Phase 1 spike.
Azure OpenAI access not available Medium Low AI security prioritisation degrades gracefully — SAST still runs, findings just aren't re-ranked. Remove the OpenAI step temporarily until access is provisioned.
Anomaly threshold too aggressive in Prod High Medium Start with threshold = 0.9 (conservative) and reduce gradually over 4 weeks of real deployments. Monitor score logs before adjusting.
Test selector misses coverage gaps Medium Medium Run the full test suite for the first 3–4 pipeline runs to validate that the selector's subset produces the same pass/fail outcome as the full suite.
Service principal permissions insufficient Low High Confirm the service connections have Contributor on the target resource groups and that the managed identity has AcrPush on ACR and Key Vault Secrets User before first run.
