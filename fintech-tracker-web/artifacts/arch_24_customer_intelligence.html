01System Overview

The AI Customer Intelligence Layer (UC24) is a unified customer profile platform purpose-built for South African fintech. It aggregates signals from all customer touchpoints — banking core, telephony, support desk, web analytics, and transaction ledger — into a single, authoritative golden record, enriched continuously by AI inference. The platform resolves identity across fragmented data sources, maintains a POPIA-compliant consent ledger, and exposes actionable intelligence via REST and GraphQL APIs consumed by downstream products including ARIA (UC18) and PayGuard (UC16).

The architecture is composed of six ordered layers, each with a discrete responsibility and clean interface contract. Data flows unidirectionally from ingestion to intelligence, with a bidirectional integration bus enabling real-time feedback loops between sibling use cases.

02Core Components
🕵
Entity Resolution Engine

The Entity Resolution Engine (ERE) is the identity backbone of the platform. It applies both deterministic and probabilistic matching strategies to identify that records across disparate source systems refer to the same individual. Deterministic rules match on exact government-issued ID numbers (RSA ID, passport), verified email addresses, and confirmed mobile numbers. Probabilistic scoring uses a weighted Jaro-Winkler similarity model over name, date of birth, and device fingerprint to handle data quality variance common in legacy banking core exports.

Each identity candidate pair is assigned a confidence score between 0.0 and 1.0. Pairs above threshold 0.85 are automatically merged; pairs in the 0.60–0.85 range are flagged for human review via an audit queue. The golden record selection algorithm applies a recency-weighted source priority: banking core > KYC provider > telephony > support desk. Deduplication runs continuously as a Kafka Streams topology, ensuring new events trigger immediate re-evaluation of identity clusters.

Unified Profile Store

The Unified Profile Store is event-sourced: every change to a customer profile is appended as an immutable event, enabling complete audit replay at any point in time. The current profile state is a materialised view derived from the event stream. PostgreSQL serves as the primary durable store; Redis caches hot profiles with a TTL-based invalidation strategy keyed on profile version.

The POPIA Consent Ledger is an embedded, append-only sub-store that records every consent grant and withdrawal, the purpose of processing, data categories covered, and the timestamp. The right-to-erasure orchestrator propagates deletion requests across all integrated systems, verifies acknowledgement receipts, and logs the erasure event chain into the audit trail.

Behavioural Signal Ingestion

All customer-generating systems publish structured events to Apache Kafka topics partitioned by customerId. A normaliser service (Python/FastAPI) consumes from each source topic, applies schema validation, enriches with a sourceSystemId and ingestionTimestamp, and produces a normalised event onto the unified customer.events.v1 topic. The banking core connector handles T24/Finacle CDC exports; the telephony adapter processes ARIA call completion webhooks; the support desk adapter consumes Zendesk event hooks; web analytics events are streamed from a server-side tracking pixel.

The transaction ledger ingestion path applies PCI-DSS field masking at the normaliser boundary — PANs are truncated to last 4 digits before entering the profile store. Dead-letter queues capture events that fail schema validation, with alerting and replay tooling surfaced via CloudWatch dashboards.

🧠
AI Intelligence Engine

The AI Intelligence Engine runs four concurrent inference pipelines. The Next-Best-Action (NBA) model combines a LightGBM ranker over structured features (recency, frequency, monetary, product holdings, channel preference) with a GPT-4o LLM layer that generates natural-language action descriptions and personalised rationale surfaced in agent UIs. Features are computed via a real-time feature store backed by Redis.

The Churn Prediction model is a gradient-boosted binary classifier retrained weekly on 90-day lookback windows, scoring each customer daily. Product Affinity Scoring uses a matrix factorisation model (ALS) over co-occurrence data to rank product categories. Customer Lifetime Value (CLV) estimation applies a BG/NBD + Gamma-Gamma pipeline. All model outputs and confidence intervals are stored back into the profile store as inference artefacts with model version provenance.

Customer embedding vectors (1536-dim) generated from interaction history via OpenAI embeddings are stored in Pinecone and used for similarity search — powering segment discovery and next-best-action cold-start resolution.

POPIA Compliance Module

The POPIA Compliance Module enforces the Protection of Personal Information Act (Act 4 of 2013) as a first-class platform concern. Consent is captured at the point of customer interaction via a consent API that records the lawful basis, purpose category, data subjects involved, and retention period. Consent state is propagated in real-time to all downstream integrated systems via a consent.events Kafka topic.

The Right-to-Erasure Orchestrator implements a two-phase deletion protocol: Phase 1 pseudonymises the profile in the primary store and suspends all inference pipelines for the subject; Phase 2 dispatches erasure requests to all eight integrated systems, collects cryptographic acknowledgements, and seals the erasure record. The sealed record is retained (without PII) as proof-of-compliance for the FSCA-required 5-year audit window.

Integration Bus

The Integration Bus provides bi-directional adapter pairs for all eight integrated systems, each with independent schema contracts, retry policies, and circuit breakers. The ARIA (UC18) adapter consumes call-completed events from the ARIA voice platform, extracts intent classifications and sentiment scores, and appends them to the customer interaction timeline. In the reverse direction, it serves enriched customer context to ARIA agents at call-start via a push-ahead cache warmed 2 seconds before connection.

The PayGuard (UC16) adapter ingests real-time fraud signal events and updates the customer riskProfile.fraudScore field, triggering downstream churn and NBA model re-scoring if the delta exceeds a configured threshold. The banking core adapter supports both real-time CDC (Debezium) and batch overnight feeds. All adapter telemetry is emitted to CloudWatch for SLA monitoring.

🌏
Customer 360 API

The Customer 360 API is the primary external interface, implemented with FastAPI (REST) and Strawberry (GraphQL). All endpoints require mTLS client certificates and JWT bearer tokens with RBAC scope enforcement. Responses are served from the Redis profile cache with a stale-while-revalidate pattern; cache misses trigger a synchronous profile hydration from PostgreSQL with a 200ms p99 budget enforced via a timeout circuit breaker.

Every API call is audit-logged — including the caller identity, requested resource, response code, and latency — to an immutable CloudWatch Logs stream. Rate limiting applies per-consumer-key at 1,000 RPM for read endpoints and 200 RPM for write endpoints. GraphQL persisted queries are enforced in production to prevent arbitrary depth queries from degrading latency SLAs.

06Deployment Architecture

The platform is deployed on AWS within the af-south-1 (Cape Town) region to satisfy SARB and FSCA data residency requirements. All services run as containerised workloads on ECS Fargate — no persistent EC2 instances. Infrastructure is defined in Terraform with GitOps-driven promotion across dev → staging → production environments gated by the DevSecOps Security Gate (UC23).

07Security Architecture
🔐
Transport & Service Authentication
  • 1mTLS enforced on all service-to-service communication — ACM Private CA issues certificates with 90-day rotation
  • 2JWT bearer tokens (RS256, 15-min expiry) required for all API calls; issued by the platform IdP with RBAC claims embedded
  • 3External-facing endpoints behind AWS API Gateway with WAF rules — OWASP Top 10 and rate-limiting at the edge
  • 4VPC with private subnets — no service directly reachable from the public internet; all ingress via ALB + NLB
👁
Data Protection & PII Controls
  • 1Field-level encryption for PII at rest — RSA-ID, passport, full name, DOB encrypted with customer-specific KMS data keys
  • 2PCI-DSS PANs masked at normaliser boundary — only last 4 digits enter the profile store; no full PAN stored
  • 3Column-level PostgreSQL encryption for consentHistory and identifiers tables using pgcrypto
  • 4Data minimisation enforced in API responses — fields returned only if RBAC scope explicitly grants access
📋
RBAC & Access Control
  • 1Scoped RBAC: customer:read, customer:write, customer:erasure — least-privilege, reviewed quarterly
  • 2Service accounts use IAM roles (ECS task roles) — no static credentials; short-lived STS tokens
  • 3Admin operations (erasure approval, role grant) require dual-sign from two authorised principals
  • 4Break-glass procedure documented and tested quarterly; emergency access triggers PagerDuty alert
📄
Audit Trail & Compliance
  • 1Immutable audit trail — every profile read, write, and erasure logged to CloudWatch Logs with write-once retention (5 years)
  • 2CloudTrail enabled for all AWS API calls; S3 audit bucket with Object Lock (COMPLIANCE mode, 5yr)
  • 3POPIA erasure records retained as sealed, PII-free proof-of-compliance artefacts for FSCA audit window
  • 4Quarterly POPIA compliance review automated via Regulatory Radar (UC22) integration
