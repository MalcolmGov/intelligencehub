Section 01
Threat Model Scope & Methodology

Scope, assumptions and threat modelling approach.

Important: This threat model covers the POPIA Scanner system itself — the scanner that analyses source code for compliance issues. The scanner has privileged read access to source repositories and processes potentially sensitive data schemas, making it a high-value target that must be secured to the same standard it enforces.
🎯
Scope

Scanner Engine API, PII Detector, Consent Analyser, Data Flow Mapper, Report Generator, CI/CD Integration Layer, evidence store, Jira integration, IR notification endpoint, and all trust boundaries between components.

📐
Methodology

STRIDE threat categorisation applied per component. CVSS 3.1 base score calculated for each threat. Risk register maintained with residual risk after mitigation. Reviewed against OWASP Top 10 and NIST SP 800-30.

Section 03
STRIDE Threat Analysis

Full STRIDE analysis applied to each component of the POPIA Scanner system.

ID STRIDE Category Component Threat Description CVSS 3.1 Severity Mitigation
TM-001 Spoofing API Gateway Attacker forges JWT token to impersonate a privileged Compliance Officer account and exfiltrate all scan reports containing sensitive schema metadata. 9.1 Critical RS256 JWT with short TTL (15min), IdP token validation, refresh token rotation, anomaly detection on access patterns.
TM-002 Spoofing CI/CD Integration Malicious GitHub Actions workflow spoofs the POPIA scanner action, injecting a backdoored scanner that suppresses findings or exfiltrates source code. 8.2 High Pin action to SHA hash (not tag), Cosign signature verification, OIDC token for action identity, branch protection rules.
TM-003 Tampering Scanner Engine Attacker with write access to scanner config tampers with PII detection patterns to exclude SA ID numbers or bank account patterns from detection, creating compliance blind spots. 9.3 Critical Config stored in signed, immutable ConfigMaps. Config changes require dual approval. HMAC integrity check on pattern files at load time. Audit log all config changes.
TM-004 Tampering Evidence Store Post-scan report tampering to remove critical findings before regulatory submission — creating a falsified compliance record. 9.8 Critical Reports content-addressed (SHA-256 hash). Evidence store write-once WORM policy. S3 Object Lock / Azure Immutable Blob Storage. Independent hash verification before IR submission.
TM-005 Tampering Jira Integration Attacker intercepts Jira API call to downgrade severity of automatically-created remediation tickets, delaying compliance fixes. 6.1 Medium mTLS for Jira API calls. Ticket severity derived from immutable findings manifest. Jira webhook verification for any severity changes. Compliance Officer notification on ticket modification.
TM-006 Repudiation Audit Trail Developer denies initiating a scan that exposed a compliance gap, or Compliance Officer denies acknowledging a critical finding — no non-repudiation mechanism in place. 7.5 High Immutable audit log (Azure Monitor / CloudWatch) with user identity from IdP. Digital signatures on report acknowledgement actions. SIEM alert on audit log deletion attempts.
TM-007 Repudiation IR Notification Organisation denies having sent (or not sent) a section 22 breach notification to the Information Regulator — no timestamped delivery receipt. 8.0 High Signed notification payloads. Store IR API response with timestamp and status code. Notification attempt logged to immutable audit trail. Email confirmation to DPO on send.
TM-008 Info Disclosure PII Detector PII detector logs raw matched strings (SA ID, bank account numbers) to application logs during debugging, creating a secondary exposure of the very PII it was scanning for. 9.6 Critical Structured logging with explicit PII redaction layer. Log level enforcement (never DEBUG in prod). Log scanning on egress. Automated test to assert no PII appears in log output.
TM-009 Info Disclosure Report Generator Generated reports include raw code snippets containing actual PII values (e.g., sample data in unit tests) — report becomes a PII disclosure document. 8.4 High Reports include only: file path, line number, pattern type, confidence score — never raw matched text. Masking enforced at findings aggregator layer. Report content review checklist.
TM-010 Info Disclosure API Gateway Verbose API error messages expose internal system architecture, database schema names, or file system paths — enabling targeted attacks. 5.3 Medium Generic error responses to clients. Full error details logged server-side only. Custom exception handler strips internal context. WAF blocks response containing internal IP/path patterns.
TM-011 Info Disclosure Git Clone Source code cloned for scanning contains .env files or hardcoded secrets — scanner worker has read access to secrets not relevant to POPIA compliance. 7.8 High Scanner pod has no internet egress. Secrets detected are reported as findings but never stored. Gitleaks integrated as pre-processing step. Pod filesystem wiped on completion.
TM-012 Denial of Service Scanner Engine Attacker submits scan job against a repository with millions of files, exhausting scanner compute/memory resources and blocking legitimate compliance scans. 7.5 High Scan job resource limits (CPU/memory via K8s ResourceQuota). Max file count and repo size enforced pre-clone. Rate limiting on /api/v1/scan endpoint. Queue depth monitoring with alert.
TM-013 Denial of Service Report Generator ReDoS attack — maliciously crafted source code with pathological regex backtracking patterns causes PII detection regex engine to hang indefinitely. 6.5 Medium Timeout wrapper around all regex operations (5s max per file). Use linear-time regex engine (Google RE2 via Python). Fuzz testing of regex patterns in CI pipeline.
TM-014 Elevation of Privilege K8s Deployment Scanner pod escapes container namespace due to misconfigured securityContext (e.g., running as root, privileged:true), gaining node-level access to all namespaces. 9.0 Critical PodSecurityContext: runAsNonRoot, readOnlyRootFilesystem, drop ALL capabilities. OPA Gatekeeper policy enforcement. Regular K8s CIS benchmark scan. No privileged pods allowed in scanner namespace.
TM-015 Elevation of Privilege API Gateway Insecure direct object reference (IDOR) on /api/v1/scan/{scan_id} — Developer can access scan results from other teams by enumerating scan IDs. 7.6 High Scan IDs are UUIDs (not sequential). Ownership check enforced server-side: scan result returned only if requesting user's org matches scan owner org. Unit and integration tests for IDOR.
TM-016 Elevation of Privilege CI/CD Integration GitHub Actions workflow with GITHUB_TOKEN has excessive permissions — scanner action reads GITHUB_TOKEN and uses it to push code or modify branch protection rules. 6.8 Medium GITHUB_TOKEN permissions scoped to minimum required (contents:read, security-events:write). Actions use OIDC instead of long-lived tokens. Permissions audited in workflow YAML.
TM-017 Low Risk Report Download Compliance report download URL is guessable and shared externally, allowing unauthorised parties to view compliance gap reports. 3.5 Low Pre-signed URLs with 1-hour expiry and IP binding. Download logged with requester identity. Reports not publicly accessible without authentication.
TM-018 Low Risk Health Endpoint Unauthenticated /api/v1/health endpoint reveals version information that could assist in targeted vulnerability exploitation. 2.3 Low Health endpoint returns only status:ok — no version in production response. Version exposed only on internal health endpoint (cluster-internal only, not externally routed).
TM-019 Low Risk Audit Logs Audit logs consume excessive storage over time due to high scan volume, causing log rotation that deletes compliance-relevant records before 3-year retention period. 3.1 Low Audit logs archived to low-cost storage (Glacier / Azure Archive) after 90 days. Retention policy enforced by platform. Alert when log storage exceeds 80% capacity.
