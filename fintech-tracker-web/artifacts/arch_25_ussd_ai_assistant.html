USSD AI Assistant Architecture

Conversational intelligence over USSD — bringing AI-driven financial services to 2G feature phones across MTN's 17-market footprint without internet connectivity.

Status: Draft v0.9 Author: Platform Architecture Team Date: 2026-05-10 Depends On: UC16-PayGuard, UC24-CustomerIntel Classification: Internal — Confidential
🌐
Architecture Overview

Problem Statement

USSD remains the primary digital channel for MTN MoMo subscribers in low-connectivity markets (Ghana, Uganda, Cameroon, Rwanda, Ivory Coast, et al.). Traditional USSD is a rigid tree-menu system — users must memorise option codes and cannot perform complex or multi-step transactions conversationally. UC25 introduces a Natural Language Understanding layer over USSD that lets subscribers express intent in their own words (in English, French, or a local language), have that intent resolved to a MoMo API action, and receive a concise, formatted USSD response — all within the 182-character USSD message constraint and sub-2-second latency budget.

Business Objectives

  • Increase MoMo active usage by 18% in feature-phone segments
  • Reduce USSD session abandonment rate from ~34% to below 15%
  • Support at least 12 languages across 17 OpCo markets
  • Enable complex transactions (loan, savings, bill pay) over USSD without 5-level menus
  • Feed interaction telemetry into UC24 Customer Intelligence

Scope

  • AI-powered session handler for inbound USSD sessions
  • Multilingual NLU pipeline (mBERT / XLM-R fine-tuned)
  • Intent-to-MoMo-API dispatch layer
  • Graceful fallback to legacy USSD tree menus
  • Per-OpCo gateway SDK adapters (Ericsson, Huawei, custom)
  • Integration with UC16 PayGuard for fraud pre-screening
  • Integration with UC24 for customer personalisation signals

Constraints

  • USSD response payload ≤ 182 characters
  • Round-trip latency budget: 1 800 ms (P95)
  • No internet at handset — pure GSM-SS7 transport
  • Session TTL governed by telecom operator (60–180 s)
  • Zero PII in application logs — regulatory requirement (NDPR, DPA)
  • Must operate in active-active across two AWS regions
⚙
Design Principles

Conversational Simplicity

Every AI interpretation must produce a response readable on a 2G Nokia screen. Complexity lives in the backend, not the UI.

Graceful Degradation

If NLU confidence falls below threshold or latency is at risk, the system falls back instantly to deterministic menu trees — no user-visible failure.

Language Parity

A subscriber in Swahili, Hausa, or Twi receives the same quality of service as one in English or French.

Privacy-by-Architecture

Session data is encrypted at rest and in transit. No MSISDN or financial amounts are written to application logs — only opaque session IDs.

OpCo Autonomy

Each MTN subsidiary can override intents, response templates, and fallback logic via per-OpCo configuration without platform code changes.

Idempotent Dispatch

Every MoMo API call is guarded by an idempotency key derived from session + intent hash, preventing duplicate financial transactions on retry.

System Components

USSD Gateway Adapter

Transport normalisation & OpCo routing

Translates proprietary USSD gateway protocols (Ericsson UCP, Huawei USSD-GW, custom REST) into a unified internal UssdSession event. Handles session open/continue/close lifecycle, MSISDN hashing (SHA-256 with per-OpCo salt), and OpCo identification via PLMN prefix routing table.

Python FastAPI Per-OpCo SDK PLMN routing MSISDN hashing

Session Manager

Stateful session tracking — Redis Cluster

Maintains the full conversation state across USSD hops. Each session is stored as a Redis hash keyed by session:{opco}:{hash(msisdn)}:{ussd_session_id} with TTL matching the network gateway timeout (default 120 s). Stores: current dialogue state, entity slots (amount, beneficiary, service code), NLU turn history, and idempotency keys.

  • Redis Cluster — 3 shards, 2 replicas each
  • Encrypted at rest (AES-256) via Redis TLS + KMS
  • Lua scripting for atomic slot-fill + state transitions
  • Keyspace notifications for session expiry alerts
Redis 7 Cluster AES-256 at rest Lua atomics

NLU Engine

Multilingual intent & entity extraction

Fine-tuned multilingual transformer (mBERT or XLM-RoBERTa depending on OpCo language mix) hosted on Triton Inference Server with ONNX runtime. Performs intent classification (28 intents across 6 domains) and slot filling (amount, currency, beneficiary, service provider, date). Outputs a structured NluResult with confidence score per intent.

  • Supported languages: English, French, Swahili, Hausa, Twi, Kinyarwanda, Lingala, Zulu, Xhosa, Amharic, Yoruba, Igbo
  • Inference latency: < 180 ms P95 on A10G GPU (batch=1)
  • Confidence threshold: 0.65 (configurable per OpCo)
  • Fallback: rule-based keyword extractor below threshold
mBERT / XLM-R Triton Server ONNX Runtime 12 languages

Intent Dispatcher

Route intents to MoMo capabilities

Maps NLU-classified intents to MoMo API operations. Enforces business rules (daily limits, KYC tier, market-specific product availability). Calls PayGuard (UC16) fraud pre-screen for monetary intents before dispatch. Handles multi-turn intent resolution when required slots are missing (e.g., "send money" without beneficiary triggers entity clarification turn).

  • Intent catalogue: SendMoney, CheckBalance, PayBill, BuyAirtime, MicroLoan, SavingsDeposit, MiniStatement, PinChange, HelpMenu, LanguageSwitch, …
  • Per-OpCo product availability matrix (config-driven)
  • PayGuard integration: synchronous pre-screen < 80 ms
  • Idempotency guard using session+intent+amount hash
Rule + ML routing PayGuard UC16 Idempotency Multi-turn

MoMo API Client

Abstraction over per-OpCo MoMo backends

Provides a unified Python async client over the heterogeneous MoMo API landscape (MTN MOMO Open API v2, legacy USSD SMSC bridge APIs, and country-specific extensions). Handles OAuth2 token refresh with per-OpCo API keys stored in AWS Secrets Manager. Circuit-breaker pattern with exponential backoff. All financial amounts treated as Decimal to avoid float rounding errors.

MoMo Open API v2 OAuth2 Circuit breaker Decimal math

Response Formatter

USSD-compliant message templating

Compresses structured API responses into USSD-compatible messages (≤ 182 chars, GSM-7 charset). Uses per-language, per-OpCo Jinja2 templates with dynamic truncation logic. Appends session navigation options (CON for continue, END for terminate). Handles currency formatting per market (NGN, GHS, UGX, etc.) and number localisation.

  • Template engine: Jinja2 with custom USSD filters
  • Charset: GSM-7 (160 chars single, 182 extended)
  • Fallback truncation preserves key financial figures
Jinja2 GSM-7 Multi-currency

Language Detector

Automatic language identification

Lightweight langdetect model (fastText LID-176) runs before NLU to identify the script/language of the subscriber input. Result stored in session state and used to route to the correct NLU model shard and response template set. Language can be explicitly overridden by subscriber via "switch to English" or "passer en français" type inputs.

fastText LID-176 < 5 ms latency Explicit override

Fallback Menu Generator

Deterministic USSD tree fallback

Generates a traditional numbered USSD menu from a per-OpCo menu configuration (JSON/YAML). Invoked when: NLU confidence below threshold, inference timeout, MoMo API error that cannot be retried, or subscriber explicitly requests menu mode. Ensures 100% functional coverage independent of AI availability. Designed for zero-latency render (no I/O, pure in-memory config lookup).

Session State Machine

Each USSD session is modelled as a finite state machine persisted in Redis. Transitions are atomic (Lua scripts). State determines which NLU context, slot-fill prompts, and response templates are applied. The machine supports concurrent clarification sub-states (e.g., confirming beneficiary while awaiting amount).

INIT
Session opened. Language detection in progress. No intent assigned.
→ LANG_CONFIRMED on lang detect
→ FALLBACK on detect error
LANG_CONFIRMED
Language identified. Awaiting first subscriber utterance for NLU classification.
→ INTENT_RESOLVED on high-conf NLU
→ CLARIFYING on low-conf or partial
→ FALLBACK on timeout
CLARIFYING
Asking subscriber for missing slots (beneficiary, amount, PIN confirmation). Multi-turn sub-loop.
→ INTENT_RESOLVED on all slots filled
→ FALLBACK on 3 failed clarifications
→ CANCELLED on subscriber cancel keyword
INTENT_RESOLVED
Full intent + entity set confirmed. Awaiting PayGuard pre-screen and MoMo dispatch.
→ FRAUD_SCREENED on PayGuard clear
→ BLOCKED on PayGuard reject
FRAUD_SCREENED
PayGuard cleared the transaction. MoMo Core API call in flight.
→ COMPLETED on MoMo success
→ PENDING on MoMo async accept
→ FAILED on MoMo error
PENDING
MoMo transaction accepted asynchronously. Session held open for callback or subscriber poll.
→ COMPLETED on callback received
→ FAILED on timeout/callback error
COMPLETED
Transaction succeeded. Success response formatted and sent. Session closing (END signal).
→ CLOSED on gateway END
FAILED
Transaction failed. Error response sent with retry or menu option. Idempotency key invalidated.
→ INTENT_RESOLVED on retry
→ FALLBACK on subscriber fallback choice
FALLBACK
Deterministic USSD menu injected. NLU layer bypassed. Legacy option tree active.
→ COMPLETED on successful legacy flow
→ CLOSED on session expiry
BLOCKED
PayGuard rejected the transaction. Subscriber informed. Session ends with fraud advisory.
→ CLOSED (terminal)
CANCELLED
Subscriber cancelled or used cancel keyword. State wiped. Session closed cleanly.
→ CLOSED (terminal)
CLOSED
Terminal state. Redis TTL runs down. Telemetry event emitted to Kafka. No further transitions.

Key Code Patterns

Session Handler — Core Entry Point (Python FastAPI)

# ussd_ai_assistant/handlers/session_handler.py from fastapi import APIRouter, Depends, HTTPException from app.models import UssdRequest, UssdResponse from app.services import ( SessionManager, LanguageDetector, NluEngine, IntentDispatcher, ResponseFormatter, FallbackMenuGenerator ) from app.config import OpCoConfig import asyncio, logging router = APIRouter() log = logging.getLogger("ussd.session") # no PII in log records @router.post("/ussd/session") async def handle_ussd_session( req: UssdRequest, session_mgr: SessionManager = Depends(), lang_det: LanguageDetector = Depends(), nlu: NluEngine = Depends(), dispatcher: IntentDispatcher = Depends(), formatter: ResponseFormatter = Depends(), fallback: FallbackMenuGenerator = Depends(), ) -> UssdResponse: opco_cfg: OpCoConfig = OpCoConfig.for_plmn(req.plmn) session = await session_mgr.get_or_create(req.session_id, opco_cfg) try: # 1. Language detection (5 ms) if session.language is None: session.language = await lang_det.detect(req.user_input) # 2. NLU classification (≤ 180 ms) nlu_result = await asyncio.wait_for( nlu.classify(req.user_input, session.language, session.turn_history), timeout=opco_cfg.nlu_timeout_s ) # 3. Confidence gate → fallback if below threshold if nlu_result.confidence < opco_cfg.confidence_threshold: menu = fallback.generate(session.state, opco_cfg) return formatter.as_ussd(menu, session, session_type="CON") # 4. Intent dispatch (includes PayGuard pre-screen for monetary) dispatch_result = await dispatcher.dispatch(nlu_result, session, opco_cfg) # 5. Format response ≤ 182 chars return formatter.as_ussd(dispatch_result, session, language=session.language, session_type=dispatch_result.session_type) except asyncio.TimeoutError: log.warning("nlu_timeout session_id=%s opco=%s", req.session_id, opco_cfg.opco_id) menu = fallback.generate(session.state, opco_cfg) return formatter.as_ussd(menu, session, session_type="CON") except Exception as exc: log.error("session_error session_id=%s err=%s", req.session_id, type(exc).__name__) raise HTTPException(status_code=500, detail="USSD_SESSION_ERROR") finally: await session_mgr.persist(session) # atomic Redis write

Redis Session Key Schema

# Key format (no raw MSISDN stored) session:{opco_id}:{sha256(msisdn + opco_salt)[:16]}:{gateway_session_id} # Redis hash fields state → ENUM string (INIT, LANG_CONFIRMED, CLARIFYING, …) language → ISO 639-1 code (en, fr, sw, ha, …) turn_history → JSON array of {role, utterance_embedding_hash, intent} slots → JSON {amount: null, beneficiary_hash: null, service: null} idempotency_key → sha256(session_id + intent + amount + timestamp_minute) opco_id → string (MTN_GH, MTN_UG, MTN_NG, …) created_at → Unix epoch (int) TTL → 120 seconds (set on every write — sliding expiry)

Security Architecture

PII Protection — No-Log Mandate

  • MSISDN is hashed (SHA-256 + per-OpCo secret salt) at the Gateway Adapter boundary. Raw MSISDN never enters application code.
  • Financial amounts are excluded from all log statements. Only opaque session IDs and intent categories appear in logs.
  • Beneficiary identifiers are hashed before storage in Redis session slots.
  • Log schema enforced via a custom Pydantic log record model — fields not on the allowlist are silently dropped before emission.
  • OpenSearch index mappings configured to reject fields containing known PII patterns (phone number regex, email regex).

Encrypted Session State

  • Redis Cluster configured with TLS 1.3 in-transit encryption.
  • At-rest encryption via AWS KMS CMK per OpCo — Redis persistence (RDB/AOF) encrypted at block-device level.
  • Sensitive slot values (amounts, beneficiary hashes) additionally envelope-encrypted with a session-scoped DEK derived from KMS.
  • DEK discarded on session CLOSED state — forward secrecy for session data.

Fraud Pre-Screening (UC16 PayGuard)

  • Every monetary intent (SendMoney, PayBill, BuyAirtime, Loan) triggers a synchronous PayGuard call before MoMo dispatch.
  • PayGuard receives: hashed MSISDN, intent type, amount, currency, beneficiary hash, OpCo, and time-of-day bucket.
  • PayGuard returns: CLEAR / REVIEW / BLOCK with a risk score. BLOCK transitions session to BLOCKED state immediately.
  • PayGuard SLA ≤ 80 ms P95 — guarded by circuit breaker; on PayGuard unavailability, high-risk transactions are held in PENDING until availability restored.

API & Transport Security

  • All internal service-to-service communication via mTLS (Envoy sidecar in App Mesh).
  • USSD Gateway Adapter authenticates gateway callbacks via HMAC-SHA256 shared secret per OpCo, stored in AWS Secrets Manager.
  • MoMo API Client uses OAuth2 client credentials per OpCo; tokens cached in Redis with 5-minute expiry buffer.
  • Per-OpCo API key rotation supported with zero-downtime dual-key window.
  • Network policies restrict pod-to-pod traffic to declared service graph only.

Idempotency & Replay Protection

  • Idempotency key = SHA-256(session_id + intent + amount_cents + minute_bucket).
  • Keys stored in Redis with 10-minute TTL; duplicate requests within window return cached response without re-calling MoMo.
  • USSD gateway retries (common on poor signal) are safely handled without double-debiting.

Audit & Compliance

  • All financial intent outcomes written to immutable audit log (Kafka → S3 → Glacier) with 7-year retention per financial regulation.
  • Audit records contain: session_id, opco, intent, outcome, timestamp — never PII.
  • SOC2 Type II controls applied; annual pen-test scope includes USSD AI layer.
  • NDPR (Nigeria), DPA (Uganda/Kenya), and Cameroonian data law compliance validated per-OpCo.

System Integrations
🛡

UC16 PayGuard — Fraud Pre-Screening

PayGuard is invoked synchronously by the Intent Dispatcher for every monetary intent before the MoMo Core API call is made. The integration uses a gRPC service call over the internal App Mesh with mTLS.

  • Request payload: hashed MSISDN, OpCo ID, intent type, amount (integer cents), beneficiary hash, device fingerprint (not available over USSD — absent field), time-of-day bucket
  • Response: {verdict: CLEAR|REVIEW|BLOCK, risk_score: 0.0–1.0, rule_id: string}
  • CLEAR: proceed to MoMo Core. REVIEW: proceed but flag for manual review in PayGuard dashboard. BLOCK: reject immediately, session moves to BLOCKED state
  • SLA: ≤ 80 ms P95. Circuit breaker: open after 5 consecutive failures — on open, high-value transactions (> threshold) are PENDING; low-value proceed with REVIEW flag
📊

UC24 Customer Intelligence — Personalisation Signals

At session INIT, the AI Session Handler fetches a lightweight personalisation context from UC24 Customer Intelligence to improve first-turn intent resolution and response personalisation.

  • Fetch: preferred language, frequent payees (hashed), account tier, active products, last session intent, preferred airtime amount
  • Protocol: REST call to UC24 profile API, timeout 150 ms — result cached in session state; non-blocking (degraded gracefully if unavailable)
  • Write: on session CLOSED, session telemetry event published to Kafka topic ussd.session.closed.v1 — UC24 consumes this for model retraining and churn signal updates
  • Kafka schema: Avro, schema registry enforced — fields: session_id, opco_id, intent_sequence (array), language, outcome, latency_p99, turn_count, fallback_triggered (bool)
📱

MoMo Core API — Financial Operations

The MoMo API Client wraps the MTN MoMo Open API v2 (and legacy variants) providing a unified async interface for all financial operations.

  • Operations: Collections, Disbursements, Remittances, Account Balance, Transaction Status, MicroLoan eligibility, Savings API
  • Auth: OAuth2 client credentials per OpCo; tokens stored in Redis with 5-min expiry buffer; rotation handled transparently
  • Idempotency: every call includes X-Reference-Id derived from session idempotency key
  • Error handling: 4xx errors mapped to user-friendly USSD messages; 5xx trigger exponential backoff (max 2 retries within latency budget); 3 retries exhausted → FAILED state

  • P1: NLU Triton pods < 2 available
  • P2: Fallback rate > 30% for any OpCo
  • P2: PayGuard circuit breaker OPEN
  • P2: Redis cluster replication lag > 500 ms
  • P3: MoMo API error rate > 5%

Log Strategy (OpenSearch)

  • Structured JSON logs (no PII — enforced at logger level)
  • Fields: timestamp, service, session_id, opco_id, state_transition, intent_category, latency_ms, error_type
  • Hot tier: 30 days (SSD), warm: 90 days (HDD), cold: 7 years (S3 Glacier)
  • Index lifecycle policy automated via ILM
  • PII scanner sidecar validates no phone numbers or amounts in log stream

NLU Model Monitoring

  • Confidence distribution tracked per intent, per OpCo
  • Concept drift detection: 7-day rolling confidence mean vs baseline
  • Automated retraining trigger if drift > 5% absolute
  • A/B model shadow deployment for new fine-tunes before cutover
  • Human annotation queue fed from low-confidence sessions (consent-gated)

Architecture Decision Records
ADR-25-001
Use XLM-RoBERTa over GPT-class models for USSD NLU
Accepted
Context

USSD NLU must run within a 180 ms inference budget, support 12 African languages, and be fine-tunable on proprietary MoMo transaction data. GPT-class models (GPT-4, Claude) were evaluated but present API latency, cost at scale, and data sovereignty concerns.

Decision

Use XLM-RoBERTa-base (fine-tuned per-language cluster) deployed on Triton Inference Server with ONNX export. mBERT used for OpCos with broader language mix where XLM-R per-language tuning is not yet complete.

Consequences

Inference within 180 ms P95 on A10G GPU. Requires ongoing fine-tuning pipeline investment. No dependency on external LLM API — full data sovereignty. Model quality may lag GPT-4 for edge-case utterances, mitigated by fallback menu for low-confidence outputs.

ADR-25-002
Redis for session state over DynamoDB
Accepted
Context

USSD sessions require sub-millisecond state reads on every hop (typically 3–7 hops per session). DynamoDB was considered for its managed scale and global tables.

Decision

Redis Cluster (AWS ElastiCache) chosen for session state. DynamoDB used only for long-term session audit archival after session CLOSED.

Consequences

Sub-millisecond state access (< 1 ms P99 on ElastiCache). Lua scripting enables atomic state machine transitions. Trade-off: Redis is in-memory — session data is lost on total cluster failure (mitigated by replica failover < 60 s). DynamoDB archival provides durable audit trail.

ADR-25-003
Confidence-gated fallback instead of always-on AI
Accepted
Context

Forcing NLU interpretation on all inputs risks incorrect financial transactions (wrong amount, wrong beneficiary) if confidence is low — particularly catastrophic in the MoMo context.

Decision

NLU confidence threshold of 0.65 (configurable per OpCo via AppConfig). Below threshold, deterministic USSD menu is injected. Threshold tuned per OpCo based on language model quality.

Consequences

Higher false-negative rate initially — some solvable requests fall to menu. This is acceptable: a menu is never wrong, an incorrect transaction is unrecoverable. Threshold will be relaxed as model quality improves per market.

ADR-25-004
Shared platform, per-OpCo config isolation (not multi-tenancy by cluster)
Accepted
Context

17 OpCos × dedicated clusters = prohibitive infrastructure cost and ops overhead. Full multi-tenancy on a single cluster was considered but raises blast-radius concerns.

Decision

Regional clusters (af-south-1, eu-west-1) with Kubernetes namespace isolation per OpCo. Network policies, resource quotas, and separate Redis keyspaces provide logical isolation. No cross-namespace traffic permitted.

Consequences

Significant infra cost reduction vs per-OpCo clusters. Blast radius contained to namespace level — a misconfigured OpCo cannot impact others. Trade-off: a cluster-level failure affects all OpCos in that region — mitigated by active-active cross-region routing.

ADR-25-005
Synchronous PayGuard pre-screen over async risk scoring
Accepted
Context

Async post-hoc fraud scoring would allow faster UX but would require rollback capability for fraudulent transactions already processed — complex and not universally supported by MoMo backends.

Decision

Synchronous PayGuard call before every monetary MoMo API call. PayGuard SLA capped at 80 ms P95 via dedicated circuit breaker.

Consequences

Adds 80 ms to monetary transaction path but prevents any fraudulent disbursements from reaching MoMo Core. Acceptable within overall 1 800 ms budget. If PayGuard is unavailable and circuit is open, high-value transactions are deferred — this is the correct conservative behaviour.

ADR-25-006
MSISDN hashing at Gateway boundary, never in application logs
Accepted
Context

Multiple African data protection regulations (NDPR, DPA, POPIA) require that subscriber PII not be logged or stored beyond operational necessity. MSISDN is PII.

Decision

Raw MSISDN hashed (SHA-256 + per-OpCo salt from Secrets Manager) at the first application touch-point (Gateway Adapter). Hash used as internal subscriber identifier. Salt rotation supported with dual-key window.

Consequences

Regulatory compliance met. Subscriber linkage across sessions requires access to the salt (held in Secrets Manager, audited access). Re-identification not possible without the salt. Log streams are safe for broader internal access.
