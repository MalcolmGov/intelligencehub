1. What is an SBOM & Why It's Required

Software Bill of Materials — Overview

A Software Bill of Materials (SBOM) is a formal, machine-readable inventory of all software components, libraries, and dependencies included in a software product or service. It records the name, version, supplier, licence, package URL (PURL), and known vulnerabilities for every component — from first-party code to transitive open-source dependencies.

SBOMs are required by PCI-DSS v4.0 Requirement 6.3.2, ISO 27001:2022 Annex A.8.8 (management of technical vulnerabilities), and POPIA Section 19 (security safeguards). Executive Order 14028 (US) and the EU Cyber Resilience Act (CRA) mandate SBOM production for software sold to government entities. Even where not legally mandated, SBOMs are considered baseline supply chain security hygiene for any production fintech system.

Key SBOM Use Cases

  • Vulnerability management — immediately identify all deployments affected when a new CVE is disclosed for a dependency
  • Licence compliance — audit all open-source licences in the dependency tree before a regulatory review
  • Supply chain security — detect tampering or unexpected component substitution between builds
  • PCI-DSS audit evidence — provide PCI-QSA with a complete software inventory satisfying Req 6.3.2
  • Incident response — during a breach, immediately scope which services consumed a compromised library
  • POPIA data flow — map personal data processing libraries to data subject categories for DPIA purposes
2. SBOM Format Comparison

SPDX vs CycloneDX vs SWID

The three dominant SBOM standards each have different strengths. UC23 generates both SPDX 2.3 and CycloneDX 1.5 by default. SWID is not generated but is noted for completeness as it is used in some enterprise procurement contexts.

Feature SPDX 2.3 CycloneDX 1.5 SWID
Primary Org Linux Foundation OWASP ISO/IEC 19770-2 (NIST)
Native Formats JSON, RDF, YAML, TV, XML JSON, XML, Protobuf XML only
Licence Data Full SPDX expression SPDX IDs + custom Limited
Vulnerability Data (VEX) Yes (SPDX-Lite + VEX) Yes — native VEX support No
Component Relationships DESCRIBES, CONTAINS, DEPENDS_ON Rich dependency graph Basic parent-child only
PURL Support Yes Yes — first class No
Hash Algorithms MD5, SHA-1, SHA-256, SHA-512 MD5, SHA-1, SHA-256, SHA-512, BLAKE2b SHA-256
Services & APIs No Yes — service component type No
ML Model Components No Yes — v1.5 ML extension No

Tooling Support Syft, SPDX-Tools, Tern, Trivy Syft, Trivy, cdxgen, Dependency-Track Limited OSS tooling
UC23 Generated Yes — default Yes — default No — not generated

6. SBOM Generation Automation

Syft & Trivy Commands

SBOMs are generated automatically by the security gate pipeline on every PR and push to a protected branch. The following commands are used directly or wrapped by the gate's sbom_generator.py module. They can also be run locally for development verification.

6.1 Syft — Generate SBOM from Source Directory

# Generate SPDX 2.3 JSON SBOM from Python project directory
syft dir:. --output spdx-json=sbom-spdx.json

# Generate CycloneDX 1.5 JSON SBOM from Python project directory
syft dir:. --output cyclonedx-json=sbom-cdx.json

# Generate both formats simultaneously
syft dir:. \
  --output spdx-json=sbom-spdx.json \
  --output cyclonedx-json=sbom-cdx.json

# Generate from a Docker image (post-build)
syft image:intelligencehub/uc23-gate:latest \
  --output cyclonedx-json=sbom-image-cdx.json

# Include dev dependencies (not recommended for production SBOM)
syft dir:. \
  --output spdx-json=sbom-dev-spdx.json \
  --config syft-config.yaml

6.2 Trivy — SBOM from Container Image

# Generate CycloneDX SBOM from a container image
trivy image \
  --format cyclonedx \
  --output sbom-trivy-cdx.json \
  intelligencehub/uc23-gate:latest

# Generate SPDX SBOM from a container image
trivy image \
  --format spdx-json \
  --output sbom-trivy-spdx.json \
  intelligencehub/uc23-gate:latest

# Generate SBOM + scan for vulnerabilities in one pass
trivy image \
  --format table \
  --output trivy-scan-report.txt \
  --severity CRITICAL,HIGH \
  --exit-code 1 \
  intelligencehub/uc23-gate:latest

# Scan a filesystem (for CI without Docker build)
trivy fs . \
  --format cyclonedx \
  --output sbom-fs-cdx.json

6.3 Security Gate Python Wrapper

# UC23 security gate SBOM generation module
# Invoked by GitHub Actions / Azure DevOps pipeline

python security-gate/sbom_generator.py \
  --source-dir . \
  --image intelligencehub/uc23-gate:latest \
  --output-dir ./sbom-artifacts \
  --formats spdx,cyclonedx \
  --commit-to-registry \
  --registry-url https://sbom.intelligencehub.io

# Validate generated SBOM against schema
python security-gate/sbom_validator.py \
  --sbom sbom-artifacts/sbom-cdx.json \
  --format cyclonedx \
  --strict

# Push SBOM to Dependency-Track for continuous monitoring
python security-gate/sbom_uploader.py \
  --sbom sbom-artifacts/sbom-cdx.json \
  --project-id uc23-devsecops-gate \
  --deptrack-url https://deptrack.intelligencehub.io \
  --api-key ${DEPTRACK_API_KEY}
ℹ
All generated SBOM files are attached as pipeline artifacts with a 12-month retention window. SBOMs are also committed to the sbom-registry Git repository under a path matching <service>/<year>/<month>/<build-id>/. This enables point-in-time retrieval for audit and incident response purposes.

8. SBOM Lifecycle & Update Cadence

SBOM Production, Distribution & Update Policy

SBOMs are living documents that must remain current with the deployed software. The following lifecycle defines when SBOMs are generated, validated, distributed, and archived.

Trigger
PR Merge / Build
SBOM generated automatically by Syft + Trivy on every successful build. Attached as pipeline artifact.
Validate
Schema Validation
SBOM validated against SPDX 2.3 / CycloneDX 1.5 schemas. Build fails if SBOM is malformed or incomplete.
Publish
Registry & DTrack
SBOM committed to sbom-registry repo. Pushed to Dependency-Track for continuous CVE monitoring and dashboard.
Monitor
Continuous Scan
Dependency-Track re-evaluates SBOM against NVD daily. New CVEs trigger Slack alerts and Jira tickets automatically.
Retain
12-Month Archive
SBOMs retained in immutable storage for 12 months. Accessible for PCI-QSA and ISO 27001 audits on demand.
