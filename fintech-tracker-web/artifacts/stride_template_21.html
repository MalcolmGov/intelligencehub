🔍 1. STRIDE Methodology Overview

STRIDE is a threat modelling framework developed by Microsoft that categorises threats into six types: Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, and Elevation of Privilege. Applied systematically to each component and data flow in a system, STRIDE ensures comprehensive security coverage across the attack surface. In the UC-21 AI Threat Modelling Agent, STRIDE analysis is auto-generated by the LLM on every PR.

S — Spoofing identity of a user, component, or service

T — Tampering with data at rest or in transit

R — Repudiation — denying actions without proof

I — Information Disclosure of sensitive or confidential data

D — Denial of Service — degrading system availability

E — Elevation of Privilege — gaining unauthorised access

🛡 2. STRIDE Category Detail — Fintech Context
S
Spoofing
Pretending to be someone or something else to gain access or trust
ISO 27001 A.5.15

An attacker impersonates a legitimate user, service, or API client to gain unauthorised access to financial systems or data.

Fintech Threat Examples
  • Stolen JWT token used to impersonate payment API consumer
  • Fake OAuth client registered to intercept auth codes
  • DNS spoofing redirecting payment webhooks to attacker server
  • AI model receiving spoofed architecture diagram input
Questions to Ask
  • How is the caller's identity verified at each API boundary?
  • Are service-to-service calls mutually authenticated?
  • Can tokens be replayed? What is the token lifetime?
  • Are diagram sources verified before LLM ingestion?
Example Mitigations
  • mTLS for service-to-service communication
  • Short-lived JWTs (<15 min) with refresh rotation
  • DNSSEC and certificate pinning for webhook endpoints
  • Cryptographic signing of diagram artefacts at source
T
Tampering
Maliciously modifying data, code, or configuration without authorisation
PCI-DSS 6.3.3

An attacker modifies data in transit, at rest, or in process to alter system behaviour, corrupt records, or manipulate AI outputs.

Fintech Threat Examples
  • MITM attack altering transaction amounts in API payloads
  • Prompt injection in PRD causing malicious threat model output
  • Threat register entries modified to suppress critical findings
  • Malicious draw.io diagram injecting script into threat report
Questions to Ask
  • Is all data validated and sanitised before LLM ingestion?
  • Are threat register writes authenticated and audit-logged?
  • Is TLS enforced on all API endpoints (no HTTP fallback)?
  • Can PR artefacts be modified after analysis starts?
Example Mitigations
  • TLS 1.3 with HSTS for all data-in-transit
  • HMAC signing of Threat Register entries
  • Input sanitisation and prompt injection detection layer
  • Immutable artefact snapshots pinned to git commit SHA
R
Repudiation
Denying having performed an action when no proof exists to refute the claim
PCI-DSS 10.2

A user or process denies taking an action (e.g., approving a PR with critical threats, overriding a security gate) because there is insufficient audit evidence.

Fintech Threat Examples
  • Developer denies overriding CRITICAL threat gate on a PR
  • Security analyst claims threat register was never updated
  • AI agent run log deleted before incident investigation
  • Jira ticket closure not linked back to threat register entry
Questions to Ask
  • Are all override actions logged with user identity and reason?
  • Is audit log storage tamper-evident and access-controlled?
  • Can logs be deleted by the same users who generate them?
  • Is there a complete chain of custody for each threat finding?
Example Mitigations
  • Immutable CloudTrail logs with integrity validation
  • Require written justification for all security gate overrides
  • Separate log storage role from developer/operations roles
  • Automated audit report generation for compliance reviews
I
Information Disclosure
Exposing information to individuals who are not authorised to see it
PCI-DSS 3.x

Sensitive data (cardholder data, PII, proprietary architecture, API keys) is exposed to unauthorised parties through system vulnerabilities, misconfiguration, or AI model outputs.

Fintech Threat Examples
  • PRD containing card data sent to OpenAI API without redaction
  • Threat model reports containing internal IP ranges exposed via pre-signed URL
  • Error messages leaking internal stack traces in PR comments
  • LLM training on sensitive threat data via data exfiltration
Questions to Ask
  • Is cardholder and PII data scrubbed before LLM API calls?
  • Are pre-signed URL expiry times appropriate (<1h)?
  • Do error responses contain internal system details?
  • Is OpenAI opt-out from training configured for our org?
Example Mitigations
  • PII/PAN detection and redaction before any LLM call
  • Pre-signed URL TTL <1h; no public S3 buckets
  • Generic error messages in all external-facing responses
  • OpenAI API with zero-data-retention agreement
D
Denial of Service
Degrading or denying service availability to legitimate users
ISO 27001 A.8.6

An attacker overwhelms the threat modelling service, exhausts API rate limits, or forces expensive LLM operations causing delays in the SDLC pipeline and PR blockages.

Fintech Threat Examples
  • Adversarial PR with 100MB diagram file exhausting analysis budget
  • Rapid PR spam triggering runaway OpenAI API cost
  • Redis queue flood blocking all other PR analyses
  • Recursive diagram references causing infinite parser loop
Questions to Ask
  • Are input file sizes and counts capped per run?
  • Is there a per-repository LLM token budget limit?
  • Can a single repo's job queue flood affect other repos?
  • Is there a timeout and circuit breaker on LLM calls?
Example Mitigations
  • Max input: 10MB total, 5 files per run
  • Per-repo daily token budget with hard cut-off and alert
  • Isolated job queues per repository (Redis keyspace)
  • LLM call timeout: 30s; circuit breaker on 3 consecutive failures
E
Elevation of Privilege
Gaining capabilities beyond what is authorised, escalating from low to high privilege
ISO 27001 A.8.2

An attacker (or compromised AI agent) gains access to resources or capabilities beyond their authorisation, potentially taking control of the threat modelling pipeline or downstream systems.

Fintech Threat Examples
  • Prompt injection causing the agent to call Jira API as admin
  • GitHub Actions workflow with overly broad GITHUB_TOKEN scope
  • Compromised API key used to modify the threat register directly
  • Container escape from the analysis runner to host systems
Questions to Ask
  • Does the agent's GitHub token follow least-privilege?
  • Can the agent make calls outside of its defined tool set?
  • Are Jira/Linear API keys scoped to specific projects?
  • Is the container run as non-root with read-only filesystem?
Example Mitigations
  • GITHUB_TOKEN: contents=read, pull-requests=write only
  • LangChain tool allowlist — no arbitrary code execution
  • Jira API key scoped to single project + issue create/edit only
  • Docker: non-root user, seccomp profile, no privilege escalation
🔢 3. DREAD Risk Scoring Model

DREAD provides a quantitative risk score for each threat, rated 1–10 across five dimensions. Total DREAD score = average of all five dimensions. High Risk: 7–10 | Medium: 4–6 | Low: 1–3. The AI agent auto-calculates DREAD scores for every identified threat.

DimensionAbbrev.DefinitionScore 1 (Low)Score 5 (Medium)Score 10 (High)
DamageD Potential damage if the threat is exploited Minor data exposure, no financial impact Partial service outage, limited data breach Full system compromise, cardholder data breach, regulatory fine
ReproducibilityR How easily the attack can be repeated Nearly impossible; requires specific timing or conditions Reproducible with effort; requires authenticated access Trivially reproducible; any unauthenticated user can reproduce
ExploitabilityE Skill and resources needed to exploit Nation-state actor with months of effort Skilled attacker with moderate tooling Script kiddie with public exploit code
Affected UsersA Proportion of users impacted if exploited Single user or admin account only A team or department (<20% of users) All users / all customers / entire platform
DiscoverabilityD How easily the vulnerability can be found Requires deep insider knowledge and source access Discoverable via network scanning or fuzzing Publicly documented, listed on exploit-db or CVE
Example DREAD Scoring — Payment API JWT Spoofing
DimensionScoreRationale
Damage8Allows impersonation of any user; access to transaction history and initiation capabilities
Reproducibility7If a long-lived token is stolen, attack is repeatable until token expires or is revoked
Exploitability6Requires token theft; several public tools available for JWT manipulation
Affected Users5Impact limited to the specific user whose token is stolen, but any user could be targeted
Discoverability7Long-lived JWTs in browser storage are a well-known vulnerability class; easily discoverable

🍝 4. PASTA Methodology — 7-Stage Process

PASTA (Process for Attack Simulation and Threat Analysis) is a risk-centric threat modelling framework that aligns security analysis with business objectives. Unlike STRIDE (component-focused), PASTA is attacker-centric and simulates realistic attack paths. The UC-21 agent applies PASTA as a complementary methodology to STRIDE for high-criticality systems.

1
Define Business Objectives
Identify the business goals that security must protect. For fintech: regulatory compliance (PCI-DSS), customer trust, transaction integrity, 99.99% payment uptime, and zero cardholder data breaches. These objectives drive threat prioritisation.
2
Define Technical Scope
Enumerate all systems, APIs, data stores, and third-party integrations within scope. For the AI Threat Modelling Agent: GitHub/Azure DevOps, OpenAI API, LangChain runtime, Jira/Linear, DynamoDB, Redis, and the Fargate execution environment.
3
Application Decomposition
Break the application into components, data flows, trust boundaries, and entry points. This maps directly to the Diagram Ingestion Engine output, providing the structured graph used for threat enumeration in subsequent stages.
4
Threat Analysis
Identify relevant threat agents (cybercriminals, nation-states, malicious insiders, compromised AI model inputs) and their capabilities, motivations, and likely targets. Enumerate threat scenarios from the attacker's perspective for each identified entry point.
5
Vulnerability and Weakness Analysis
Map threats to specific vulnerabilities in the system using CVSS scoring, OWASP Top 10, and CWE identifiers. For the AI agent context, include AI-specific vulnerabilities: prompt injection (CWE-20), model poisoning, and hallucination-driven false negatives in threat reports.
6
Attack Modelling and Simulation
Construct attack trees and attack paths for the highest-risk scenarios identified. Simulate how an attacker would chain multiple vulnerabilities to achieve their objective. Generate attack narratives that demonstrate exploitability in realistic conditions.
7
Risk and Impact Analysis
Quantify residual risk after proposed mitigations. Map findings against the organisation's risk appetite. Output executive risk heat map showing current threat landscape vs. acceptable risk thresholds. Feed high-risk findings into the Threat Register for tracking and remediation.
