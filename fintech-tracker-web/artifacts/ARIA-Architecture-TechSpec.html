ARIA Technical Specification v1.0

1Executive Summary

1.1 Overview

ARIA (AI Response & Incident Agent) is a voice-first AI support agent designed to empower front-office staff at South African fintech and banking institutions. ARIA intelligently routes inquiries across two core domains: IT/technical support and product/banking operations. By combining Claude's advanced natural language understanding with real-time voice processing via ElevenLabs, ARIA delivers immediate, contextually-aware responses while maintaining full audit compliance and POPIA data protection standards.

The system serves diverse user personas—from front-line tellers and relationship managers to compliance officers—reducing response times from minutes to seconds and improving first-contact resolution rates significantly. When human expertise is required, ARIA seamlessly escalates to L1/L2 support teams with full incident context and conversation history.

1.2 Architectural Rationale

This architecture was designed to meet four critical objectives:

  1. Voice-First Interaction: ElevenLabs STT/TTS provides low-latency multilingual speech processing, reducing user friction compared to text-based interfaces in a fast-paced banking environment.
  2. Knowledge Grounding: A Retrieval-Augmented Generation (RAG) pipeline ensures ARIA responses are rooted in internal knowledge bases, reducing hallucinations and maintaining institutional control over information quality.
  3. Regulatory Compliance: Native PostgreSQL audit logging, POPIA-aligned data retention, and role-based access controls are built into the core architecture rather than bolted on.
  4. Operational Reliability: Stateless microservices, horizontal scaling via containerization, and graceful escalation paths ensure 99.9% uptime and <3-second response latency under peak load.

1.3 Success Criteria

ARIA's success is measured against: (a) voice interaction latency <3 seconds end-to-end, (b) STT accuracy >95%, (c) first-contact resolution >70% for tier-1 queries, (d) zero POPIA violations, and (e) support of 500+ concurrent users during business hours.

2System Architecture Overview

ARIA operates across six interconnected layers, each with specific responsibilities and technology choices designed for resilience and compliance.

2.1 Layered Architecture

Layer 1 - User Interface: Web and mobile clients with browser-based audio capture, providing accessibility across devices.

Layer 2 - Voice Processing: ElevenLabs integration for real-time STT (inbound) and TTS (outbound), with optional transcript normalization for dialect/accent handling.

Layer 3 - AI/NLP Orchestration: Claude Sonnet API as the central intelligence engine, with intent classification, entity extraction, and context management.

Layer 4 - Knowledge Retrieval: RAG pipeline combining vector embeddings with document retrieval, ensuring responses are grounded in institutional knowledge.

Layer 5 - Integrations: Connectors to ServiceNow (incident creation), Active Directory (authentication), Teams (escalations), and optional Slack integration.

Layer 6 - Persistence: PostgreSQL for audit logs and session data, Redis for caching and rate limiting, S3 for compliant voice recording storage.

5Voice Pipeline Flow

The voice interaction pipeline is optimized for sub-3-second total latency, critical for a conversational experience in a banking environment.

5.1 Step-by-Step Flow

  1. User Speech (0-30s): User speaks their question or request naturally into the interface.
  2. Audio Capture (<100ms): Browser's Web Audio API captures raw audio stream with high fidelity.
  3. Speech-to-Text (<1.5s): Audio is sent to ElevenLabs STT API, returning a text transcript.
  4. AI Processing with RAG (<1s): Transcript is passed to Claude Sonnet, which enriches the prompt with relevant context from the vector database, performs intent classification, and generates a response.
  5. Response Text Generation (<500ms): Claude returns structured response text with escalation flags if needed.
  6. Text-to-Speech (<800ms): Response is sent to ElevenLabs TTS API, producing natural-sounding voice output in the user's preferred language.
  7. Audio Playback (<100ms): Audio is streamed to the user's speaker or headset.
Latency Optimization: ElevenLabs calls can be parallelized with Claude API calls where possible. Context retrieval from the vector database is optimized with caching; results for the same query within 15 minutes are served from Redis (sub-50ms).

6Data Architecture

6.1 Core Data Stores

PostgreSQL (Relational): Primary store for user sessions, conversation history, audit logs, incident escalations, and admin metadata. Tables include: users, sessions, conversations, audit_logs, incidents, knowledge_articles.

Redis (In-Memory): Cache layer for session tokens, vector search results, rate limiting counters, and temporary conversation context. TTL policies ensure no persistent sensitive data is stored.

S3 / Object Storage: Encrypted storage for voice recordings, document backups, and conversation transcripts (for compliance audits). Lifecycle policies ensure deletion after 90 days.

Vector Database (Pinecone/pgvector): Stores document embeddings indexed by semantic similarity, enabling fast RAG retrieval. Namespace separation by domain (IT vs. Banking).

6.2 Data Schemas (High-Level)

-- Sessions & Conversations
CREATE TABLE sessions (
    id UUID PRIMARY KEY,
    user_id UUID NOT NULL,
    started_at TIMESTAMP,
    ended_at TIMESTAMP,
    status ENUM ('active', 'closed', 'escalated')
);

CREATE TABLE conversations (
    id UUID PRIMARY KEY,
    session_id UUID REFERENCES sessions(id),
    user_message TEXT,
    ai_response TEXT,
    intent VARCHAR(100),
    escalated BOOLEAN,
    created_at TIMESTAMP
);

-- Audit Logging
CREATE TABLE audit_logs (
    id UUID PRIMARY KEY,
    user_id UUID,
    action VARCHAR(100),
    resource_type VARCHAR(50),
    resource_id UUID,
    timestamp TIMESTAMP,
    ip_address INET,

);

-- Incidents
CREATE TABLE incidents (
    id UUID PRIMARY KEY,
    ticket_id VARCHAR(50),
    priority ENUM ('P1', 'P2', 'P3', 'P4'),
    status VARCHAR(50),
    created_from_session_id UUID REFERENCES sessions(id),
    assigned_to UUID,
    created_at TIMESTAMP
);

6.4 POPIA Compliance Measures

  • Data Minimisation: ARIA collects only user ID, role, and query content—no personal identity numbers, bank account details, or biometric data.
  • Purpose Limitation: Data is used solely for support delivery and compliance auditing. Third-party sharing (e.g., ElevenLabs) is strictly contractual and minimal (e.g., audio + transcript only).
  • Encryption: All data at rest is encrypted with AES-256. Data in transit uses TLS 1.3. Voice recordings in S3 use AWS KMS.
  • Access Controls: Role-based access via Active Directory; only authorized support staff can view conversation history. Admin access is logged and audited.
  • User Rights: Users can request data export, deletion, or correction via a self-service portal. Requests are processed within 30 days.
  • Data Breach Protocol: Any unauthorized access triggers immediate notification to compliance team and affected users within 24 hours.

8Security & Compliance

8.1 POPIA (Protection of Personal Information Act) Requirements

ARIA operates under South African data protection law. Key obligations:

  • Lawfulness: Data processing must have a clear lawful basis (e.g., contract, consent, legal obligation). ARIA's basis is customer service delivery.
  • Transparency: Users receive clear, upfront notification that conversations are recorded and may be escalated to humans.
  • Data Subject Rights: Users can exercise rights to access, correct, delete, or port their data within 30 days of request.
  • Accountability: A dedicated Data Protection Officer oversees compliance; audit logs prove adherence to POPIA principles.

8.2 Encryption

Data in Transit Data at Rest
TLS 1.3 for all HTTP/API calls AES-256-GCM for databases (PostgreSQL transparent encryption)
HTTPS everywhere (HSTS enabled) AWS KMS for S3 object encryption
JWT tokens signed with RS256 Redis encrypted at rest (optional, depends on deployment)
Pinecone encrypted vectors (default) Database backups encrypted before storage

8.3 Access Control

  • Authentication: All users authenticate via Active Directory. SSO enforces MFA for sensitive roles (compliance, admin).
  • Authorization: Role-based access control (RBAC) implemented at API level. Roles: Tier-1 Support, Banking Specialist, Compliance Officer, Admin.
  • Data Access: Conversation data is visible only to the assigned support agent and compliance officers. Audit logs are immutable and admin-only.
  • Least Privilege: Service accounts run with minimal permissions. ElevenLabs API key is rotated quarterly.

8.4 Audit Trail Requirements

Every interaction with ARIA is logged immutably in PostgreSQL audit table:

  • User ID, timestamp, action type (query, escalation, data access)
  • Source IP, user agent, session ID
  • For sensitive actions: detailed before/after snapshots
  • Retention: 1 year for financial compliance; 90 days for general data

8.5 Incident Response & Breach Protocol

  • Detection: Automated alerts on suspicious activity (failed login attempts, bulk data export, unusual API calls).
  • Response: On suspected breach, isolate affected systems, preserve logs, notify DPFO within 24 hours.
  • User Notification: Affected users notified within 30 days with details of breach, data types, and remediation steps.

9.4 Disaster Recovery & High Availability

  • Database Backups: Hourly automated backups with 7-day retention; point-in-time recovery available.
  • Geographic Redundancy: Frontend on Vercel (multi-region). Backend can quickly be re-deployed to alternate region.

  • RTO/RPO: Recovery Time Objective: 15 minutes. Recovery Point Objective: <1 hour.

11Phased Rollout Plan

11.1 Phase 1: MVP - IT Support (Weeks 1-8)

Scope: ARIA handles IT/technical support queries from front-line tellers and staff.

  • Knowledge Base: 200+ IT FAQ articles, troubleshooting guides, password reset procedures
  • User Base: 50 internal testers (IT department + selected support staff)
  • Features: Voice input/output, ticket auto-creation in ServiceNow, escalation to L1
  • Testing: Closed beta, feedback loop weekly
  • Success Metrics: 90%+ user satisfaction, <3s latency, >85% queries resolved without escalation

11.2 Phase 2: Extended Scope - Banking & Product Queries (Weeks 9-20)

Scope: ARIA expands to handle product inquiries, account queries, transaction assistance.

  • Knowledge Base: Add 500+ banking FAQs, product guides, regulatory info
  • User Base: Expand to 200 internal users across all branches
  • New Features: Multi-intent handling (IT + Banking), context switching, account lookup (read-only)
  • Integration: Read-only connection to core banking system for balance/transaction info
  • Testing: Extended beta with banking ops and relationship managers
  • Success Metrics: 70%+ FCR for banking queries, <4s latency with account lookups

11.3 Phase 3: Full Production - Self-Service + Analytics (Weeks 21-32)

Scope: ARIA fully productionized for all users; added analytics and manager dashboards.

  • Rollout: Full production deployment; available during business hours (9am-5pm weekdays)
  • New Features: Compliance officer role for regulatory queries, admin dashboard with usage analytics, knowledge article suggestions based on gaps
  • Manager Portal: Branch managers see team ARIA interactions, escalation trends, performance metrics
  • Continuous Learning: Feedback loop: user corrections → knowledge base improvements → retraining
  • Success Metrics: 500+ concurrent users supported, 99.9% uptime, <3s latency maintained
