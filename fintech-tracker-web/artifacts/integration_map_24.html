🎙️
UC18 ARIA Voice Agent
Conversational AI voice system — call handling & intent resolution
Bi-directional
Data Flows
⬇ Inbound to CIL

Call-ended event → transcript summary, intent classification, sentiment score, resolution status → merged into unified customer profile

⬆ Outbound from CIL

Customer profile context → ARIA pre-call briefing: name, interaction history, product holdings, preferences, risk flags

Data Elements
transcriptSummary satisfactionScore agentId callDurationMs intentClassification sentimentScore resolutionStatus riskFlags
Protocol
REST webhooks + event-driven via Kafka
Frequency / Latency
Event-triggered; <2s post-call webhook delivery
Pattern
Event-driven · Push
Auth
HMAC-signed webhook + mTLS for Kafka
⚖️
POPIA: Call transcripts are personal information under POPIA. Requires explicit consent to record; data must be stored with purpose limitation. Retention max 12 months unless legally required longer. Transcript content must be masked for PII (ID numbers, card digits) before storage.
🔁 Error Handling: Webhook delivery failures retry with exponential backoff (3 attempts, max 30s). If pre-call briefing unavailable, ARIA falls back to static customer name only. Dead-letter queue captures failed events for replay.
🛡️
UC16 PayGuard Fraud Shield
Real-time fraud detection, AML screening & device intelligence
Bi-directional
Data Flows
⬇ Inbound to CIL

Fraud risk score, AML flag, device fingerprint, last fraud event timestamp → merged into unified customer risk profile

⬆ Outbound from CIL

Behavioural history, interaction pattern signals, channel usage, cross-product activity → enriches PayGuard risk model

Data Elements
fraudRiskScore (0–100) amlRisk deviceId deviceFingerprint lastFraudFlag amlFlagReason interactionCount channelPattern
Protocol
gRPC — low-latency binary framing
Frequency / Latency
Real-time; p99 <50ms fraud signal delivery
Pattern
Synchronous request/response + async enrichment stream
Auth
mTLS + service account JWT
⚖️
POPIA: Fraud scores and AML flags constitute processing of personal information for fraud prevention — a legitimate interest basis. Device fingerprints must be pseudonymised. Profiling for risk purposes requires disclosure in privacy notice. Cross-border transfer restriction applies if PayGuard is hosted outside RSA.
🔁 Error Handling: gRPC circuit-breaker pattern. If PayGuard is unreachable, CIL falls back to last-known risk score (max 5 min stale). Scores older than 5 min flagged as STALE in the unified profile. Alert triggers if circuit opens for >60s.

Banking Core System
Accounts, balances, product holdings & transaction history
Inbound
Data Flows
⬇ Inbound to CIL — Full Scope

Account data (account numbers, types, statuses, balances), transaction history (last 24 months), product holdings (savings, credit, investments, insurance), KYC status, credit limit, relationship start date

Data Elements
accountId accountType balance kycStatus productHoldings[] creditLimit relationshipStartDate transactionHistory
Protocol
REST API + database replication (read replica)
Frequency / Latency
Near-real-time; 5 min lag for balances; event-driven for transactions
Pattern
Pull (REST) + CDC event stream for new transactions
Auth
OAuth2 client credentials + IP allowlist
⚖️
POPIA: Financial account data is sensitive personal information. Strict purpose limitation — only used for customer-facing intelligence, not sold or profiled for third-party marketing without explicit consent. Data minimisation: CIL should not store raw transaction amounts beyond aggregated features.
🔁 Error Handling: Stale data marked with lastSyncTimestamp. If core system is unavailable, CIL serves from cache with DEGRADED flag. Automatic reconciliation job runs nightly to detect drift between CIL profile and core system.

Telephony / IVR System
Call logs, IVR paths, wait times & abandonment signals
Inbound
Data Flows
⬇ Inbound to CIL

Call logs (timestamps, ANI, DNIS), IVR menu path selections (intent tree traversal), wait time per queue, abandonment events with abandonment point, call transfer chains, callback request events

Data Elements
callId ani callTimestamp ivrPathSequence waitTimeMs abandonmentPoint queueId transferChain
Protocol
SFTP (CDR batch files) + real-time SIP events
Frequency / Latency
CDR batch: hourly; SIP events: real-time (<500ms)
Pattern
Batch (CDR) + real-time event push (SIP)
Auth
SFTP key pair + SIP trunk authentication
⚖️
POPIA: ANI (phone number) is personal information. CDR files must be encrypted at rest and in transit. IVR paths may reveal sensitive intent (e.g., "I want to cancel"). Access limited to data science and engineering roles with logged access. Retention: 6 months for CDR, 12 months for intent patterns.
🔁 Error Handling: CDR file integrity verified via checksum. Missing hourly files trigger alert within 90 min. SIP event drops caught by sequence gap detection; backfill from CDR batch within next hourly window.

Customer Support Desk
Jira Service Management / Zendesk — tickets, CSAT & resolution
Inbound
Data Flows
⬇ Inbound to CIL

Full ticket history (open, resolved, escalated), resolution times (first response + full resolution), CSAT scores per ticket, issue category taxonomy, agent assigned, SLA breach flags, linked account/product

Data Elements
ticketId issueCategory csatScore resolutionTimeMs firstResponseTimeMs slaBreach agentId escalationCount
Protocol
REST API polling + webhook on ticket close
Frequency / Latency
Polling every 15 min; close webhook <1s
Pattern
Pull (polling) + event push (ticket lifecycle)
Auth
API key + OAuth2 (Zendesk) / PAT (JSM)
⚖️
POPIA: Ticket content may contain sensitive personal information. Issue descriptions should be summarised (not stored verbatim) in CIL. CSAT scores and resolution times are aggregated. Customer identity in tickets linked via masked customer reference, not raw ID numbers.
🔁 Error Handling: Polling failures logged; retry on next cycle. Webhook failures trigger REST fallback poll within 5 min. Duplicate ticket events deduplicated by ticketId + updatedAt timestamp. Schema mismatch (JSM vs Zendesk) handled by normalization adapter.

Web & Mobile Analytics
Behavioural signals — page views, product interest, drop-off & sessions
Inbound
Data Flows
⬇ Inbound to CIL

Page view events, product page views (interest signals), funnel drop-off points, session duration, feature interaction events, app screen transitions, push notification open events, A/B test group assignments

Data Elements
sessionId pageUrl productPageViews[] dropOffPoint sessionDurationMs deviceType pushOpenRate abTestGroup
Protocol
Kafka event streaming (browser SDK + mobile SDK)
Frequency / Latency
Real-time streaming; <200ms event publish latency
Pattern
Event streaming · pub/sub · micro-batch windows
Auth
SDK API key + server-side customer ID resolution
⚖️
POPIA: Digital behaviour tracking requires POPIA-compliant cookie/consent banner. Behavioural data linked to customer identity only after explicit consent. Anonymous sessions stored without identity link until opt-in. IP addresses must be masked to subnet level before storage.
🔁 Error Handling: Kafka consumer lag monitoring — alert at >10k events backlog. SDK events buffered client-side up to 100 events if offline. Out-of-order events handled with 30s event-time windowing. Bot/crawler traffic filtered before ingestion via user-agent + behaviour heuristics.

Transaction Ledger
Payment history, merchant categories, spend patterns & recurring payments
Inbound
Data Flows
⬇ Inbound to CIL

Payment history (MCC category, amount, merchant, timestamp), merchant category spend patterns (monthly aggregates), recurring payment detection (subscriptions, debit orders), high-value transaction flags

Data Elements
transactionId mccCode merchantName amount currencyCode spendCategoryAggregates recurringFlag highValueFlag
Protocol
CDC via Debezium from PostgreSQL write-ahead log
Frequency / Latency
Near-real-time; <30s from transaction commit to CIL
Pattern
WAL-based CDC · Kafka outbox · exactly-once semantics
Auth
Debezium service account with pg_read_replication slot
⚖️
POPIA: Transaction data is highly sensitive. CIL stores aggregated spend features (category buckets, monthly totals), not raw transaction amounts or merchant names. Raw transaction data is not persisted in CIL — only derived features. Audit log required for all access to transaction-derived features.
🔁 Error Handling: Debezium slot health monitored — WAL slot lag alert at >1GB. Replication slot failure triggers fallback to hourly REST API snapshot from Banking Core. Deduplication by transactionId using idempotent Kafka topic key. Exactly-once delivery enforced via Kafka transactions.

Marketing Platform
Next-best-action signals, campaign targeting & consent enforcement
Outbound
Data Flows
⬆ Next-Best-Action

NBA signals → campaign targeting: product recommendations, churn risk score, upsell propensity scores, preferred channel for outreach

⬆ Consent Enforcement

Customer consent status → suppress non-consented contacts from all campaign sends in real-time; consent withdrawal propagates within 24h

Data Elements
customerId nextBestAction churnRiskScore upsellPropensity preferredChannel consentStatus suppressionFlag consentWithdrawnAt
Protocol
REST API batch push + real-time consent webhook
Frequency / Latency
NBA batch: daily 02:00 SAST; consent: real-time <5s
Pattern
Batch (NBA) + event push (consent) — CIL as publisher
Auth
OAuth2 + Marketing Platform API key
⚖️
POPIA: Direct marketing requires opt-in consent under POPIA Section 69. CIL is the consent authority — marketing platform must not send to suppressed contacts. Consent withdrawal is a hard stop; CIL must propagate suppression within 24 hours. NBA signals shared are aggregate scores only (not raw behaviour data).
🔁 Error Handling: NBA batch failures trigger retry with full resend next day. Consent webhook failure escalates to critical alert — marketing campaigns must pause for that customer until confirmed suppression delivered. Audit trail of all consent state changes retained for 5 years.

◎ Data Quality Requirements per Source
🏦 Banking Core System
Customer ID must be canonical and match CIL master identity key. No orphaned accounts.
Account status transitions must arrive in order — out-of-order events rejected and re-queued.
Balance figures must carry effective timestamp — CIL must not serve stale balances as current.
Product holding records must be complete — partial sets trigger data-fetch retry.
Min quality threshold
99%
💳 Transaction Ledger
Every transaction must carry a valid MCC code — null MCC classified as "Uncategorised" only after validation attempt.
Amount must be in ZAR or include currency code for FX conversion.
Duplicate transaction IDs from CDC must be idempotently handled — no double-counting in spend aggregates.
Recurring payment detection requires minimum 3-month history; new customers flagged as INSUFFICIENT_HISTORY.
Min quality threshold
99.5%
🛡️ UC16 PayGuard Fraud Shield
fraudRiskScore must be a float 0.0–100.0. Values outside range rejected with alert.
Score must carry model version and score timestamp — scores >5 min old marked STALE.
AML flag must include flag reason code from approved taxonomy — free-text reasons rejected.
Device fingerprint must be pseudonymised SHA-256 hash — raw device IDs not accepted.
Min quality threshold
99%
🎙️ UC18 ARIA Voice Agent
Transcript summaries must be <500 tokens — full transcripts not stored in CIL.
intentClassification must match approved intent taxonomy v2.x — unmapped intents flagged for taxonomy review.
satisfactionScore must be normalised 0–10; CSAT collection optional but null accepted.
callId must be globally unique and linked to telephony CDR callId for cross-source join.
Min quality threshold
97%
🎫 Customer Support Desk
Ticket must link to a canonical customer ID — unlinked tickets go into a resolution queue (not discarded).
Issue category must use normalised taxonomy across JSM and Zendesk — mapping adapter enforced at ingestion.
CSAT score is optional but must be 1–5 if present; out-of-range scores rejected.
Resolution time calculated server-side in CIL from raw timestamps — not trusted from source.
Min quality threshold
95%
📊 Web & Mobile Analytics
Events must carry resolved customerId (not just sessionId) for profile linkage — anonymous events retained separately.
Event schema must pass Avro schema registry validation — malformed events sent to DLQ.
sessionId must be consistent within a session — SDK session hijacking detection applied.
Bot/crawler traffic must be filtered before Kafka publish; CIL will reject events without valid consent token.
Min quality threshold
90%
📞 Telephony / IVR System
CDR files must be delivered hourly with checksum — missing files trigger alert; backfill from SFTP archive.
ANI (phone number) must be normalised to E.164 format before ingestion.
IVR path sequence must be valid against published IVR menu tree version — stale path sequences flagged for review.
Wait time must be in milliseconds — seconds-level values auto-converted with audit flag.
Min quality threshold
92%
📣 Marketing Platform (Outbound)
NBA signals must include model version and confidence score — low-confidence scores (<0.6) must be flagged before send.
consentStatus must be binary (true/false) — no null consent; unknown defaults to false (suppressed).
Batch push must be idempotent — marketing platform must handle duplicate customer records gracefully.
suppressionFlag changes must be acknowledged within 5 minutes — unacknowledged suppressions escalated immediately.
Min quality threshold
100%
⚡ Conflict Resolution Rules — When Sources Disagree
Data Attribute Conflicting Sources Resolution Rule Winner Notes
Customer Identity / Name Banking Core vs Support Desk vs ARIA Banking Core is authoritative for legal name. Support desk and ARIA preferred name are stored as aliases — displayed where contextually appropriate. Banking Core Preferred name from support/ARIA stored as preferredDisplayName field
Contact Phone Number Banking Core vs Telephony CDR vs ARIA Banking Core holds the KYC-verified number. Telephony ANI may differ (shared phones). CDR ANI stored as lastCallANI, not as verified contact. Banking Core ANI mismatch logged as a signal — potential fraud indicator
Fraud Risk Score PayGuard real-time vs stale cached score Most recent score wins unconditionally. Score must carry timestamp; stale scores (>5 min) marked STALE and not used for decisions — CIL re-requests fresh score. Most Recent Timestamp Never blend scores — always point-in-time latest
Account Balance Banking Core REST vs Transaction Ledger CDC Banking Core authoritative for balance. Ledger CDC used for transaction event enrichment only, not balance override. Discrepancy triggers reconciliation alert. Banking Core Balance discrepancy >R100 triggers async reconciliation job
Product Holdings Banking Core vs Transaction Ledger (inferred) Banking Core holds authoritative product register. Ledger-inferred products (e.g., merchant pattern suggests credit card) stored as inferred_holdings — not promoted to confirmed without Banking Core confirmation. Banking Core Inferred holdings used for NBA modelling; confirmed holdings for factual display
Customer Intent / Topic ARIA voice intent vs IVR path vs Support Desk issue category Most recent interaction wins for "current intent". Historical intents aggregated into intentHistory[] for trend analysis. No single source overrides another for history. Most Recent Event Intent taxonomy must be normalised across all three sources before comparison
Satisfaction Score (CSAT) Support Desk CSAT vs ARIA post-call CSAT Both scores stored independently with source tag (CSAT_DESK, CSAT_VOICE). Composite score = weighted average (0.4 desk, 0.6 voice) if both present within same 7-day window. Composite (weighted) Single-source CSAT stored as-is if only one present
Consent Status Marketing Platform consent record vs CIL consent store CIL is the consent authority. Marketing platform is a consumer of consent state, not a source. If marketing platform reports consent=true but CIL has withdrawn=true, CIL suppression wins unconditionally. CIL Consent Store POPIA requirement — data subject consent is managed centrally
Digital Behaviour / Product Interest Web analytics vs Mobile analytics vs ARIA expressed intent All three signals contribute to a product interest score. Weights: ARIA expressed intent (0.5) + web/mobile page views (0.3) + IVR path (0.2). Expressed intent always carries highest weight. Weighted Ensemble Interest scores decay over time — 30-day half-life applied to all signals
Last Interaction Date ARIA, Support Desk, Web, Telephony (all) lastInteractionDate = max(all source event timestamps). Each source also stores its own lastInteractionDate in the source-specific profile block. MAX across all sources Used for churn risk — channel-specific last interactions available for drill-down
