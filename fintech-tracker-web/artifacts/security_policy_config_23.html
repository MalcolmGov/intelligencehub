1. CVSS Threshold Policy by Environment

Environment-Specific Severity Gates

The security gate applies CVSS v3.1 blocking thresholds on a per-environment basis. Production environments enforce the most restrictive policy. Thresholds are defined in security-gate.yaml under the environments key and are validated at startup by the policy schema engine.

CVSS Severity Score Range Development Staging Production Hotfix Branch
Critical ≥ 9.0 WARN BLOCK BLOCK BLOCK
High 7.0 – 8.9 INFO WARN BLOCK BLOCK
Medium 4.0 – 6.9 INFO INFO WARN WARN
Low 0.1 – 3.9 PASS PASS INFO INFO
None 0.0 PASS PASS PASS PASS
⛔
Hardcoded Rule: Critical severity (CVSS ≥ 9.0) is blocked on ALL branches including hotfix branches. This cannot be overridden via configuration — it is enforced at the code level and the bypass token system does not accept Critical-level exemption requests. Any attempt triggers a CISO P1 incident alert within 60 seconds.

Secret Detection Override Policy

Secrets are treated as CRITICAL regardless of CVSS score — a detected secret always blocks the pipeline on all environments. There is no CVSS threshold for secrets; the detection of any secret pattern constitutes an automatic Critical finding.

Finding Type Effective Severity All Environments Exemptable
Detected Secret / Credential Critical Override BLOCK No
Hardcoded Password Critical Override BLOCK No
High-Entropy String in Config File High Env-based threshold Yes

Individual findings may be suppressed inline using approved suppression comments. Suppression comments are audited and reviewed quarterly. Mass suppression of entire rule sets requires CISO approval and is logged as a policy exception.

6. Exemption Process

Security Gate Exemption Request & Approval Workflow

An exemption allows a pipeline to merge despite a policy-blocking finding. Exemptions are time-limited, logged immutably, and are not available for Critical severity findings or detected secrets. All exemptions require a documented business justification and a remediation plan with a committed delivery date.

6.1 Exemption Request Steps

  • 1
    Identify Blocking Finding
    Review the PR security gate comment to identify the specific CVE, rule ID, or policy violation causing the block. Confirm the finding is a genuine block (not a false positive — if FP, submit via ML training feedback instead).
  • 2
    Raise Exemption Request in Jira
    Create a Jira issue in the SECU project using the Security Gate Exemption Request template. Include: CVE ID / rule ID, CVSS score, affected component, business justification, risk acceptance statement, proposed remediation date (max 30 days), and requesting engineer name.
  • 3
    Tech Lead Preliminary Review
    The requesting engineer's Tech Lead reviews the request within 1 business day. Tech Lead confirms the finding cannot be resolved before the required merge date and approves the escalation to the Security team.
  • 4
    Security Team Risk Assessment
    Security team reviews the CVSS score, exploitability (CVSS AV, AC, PR, UI vectors), existing compensating controls, and business context. Assesses whether compensating controls (WAF rule, network isolation, runtime protection) adequately reduce risk.
  • 5
    Approval Based on Severity
    High severity (7.0–8.9): CISO approval required. Medium (4.0–6.9): Security Lead approval. Low: Tech Lead approval. Critical severity exemptions are not accepted — the request will be rejected. Approval generates a signed bypass token valid for the specified duration only.
  • 6
    Bypass Token Issued & Applied
    The bypass token is added to the PR description as a structured comment SECURITY_GATE_BYPASS: <token>. The gate enforcer validates the token signature and expiry before allowing the merge. The token is single-use and expires at the specified date or when the fixing PR is merged.
  • 7
    Remediation & Closure
    The fixing PR must be merged before the exemption expiry date. The Jira SECU ticket is linked to the remediation PR and auto-closed on merge. Expired unresolved exemptions trigger a CISO notification and automatic escalation to P2 incident.

7.3 Policy Change Approval Process

Any change to threshold values, rule set enablement, or blocked package lists must follow the change management process:

  • Threshold changes (more permissive) — require CISO approval + board notification if PCI-DSS scoped
  • Threshold changes (more restrictive) — require Security Lead approval + Head of Engineering notification
  • New rule set enablement — require Security Lead approval
  • New blocked package — automated on confirmed CVE; Security Lead reviews within 24h
  • Secret pattern additions — Security Team authority; no external approval required
  • Exemption process changes — require CISO approval
