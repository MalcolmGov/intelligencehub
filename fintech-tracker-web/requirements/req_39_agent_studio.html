Executive Summary

MTN Agent Studio is an internal agentic AI platform that enables every division across MTN's 16+ business units — from Fintech and Network to Legal and HR — to deploy AI agents tailored to their workflows, without requiring deep engineering expertise or initiating individual software projects each time.

The platform is adapted from the Swifter AI Platform (an enterprise-grade agentic infrastructure built in TypeScript/Next.js 15) and re-skinned, configured and governed for MTN's internal multi-division, multi-market operating model. It provides a self-service template library, a visual DAG workflow builder, an approval gate system, a full audit trail, and RBAC-governed division isolation — all deployed on MTN's Azure cloud environment with Azure AD SSO.

Problem Statement

Current State Pain Points

🔴 Per-project engineering overhead
Every AI initiative across MTN's divisions requires a full engineering project: RFP, vendor selection, architecture review, CISO sign-off, budget approval, 6–18 months delivery. Most divisions abandon AI ideas before they reach execution.
🔴 No reusability across divisions
When Fintech builds a document processing agent, Network builds one separately, Legal builds one separately. Each pays the full engineering cost with no shared infrastructure, no shared templates, no shared governance framework.
🔴 Shadow AI proliferating
Divisions are already deploying unapproved ChatGPT integrations, Zapier workflows and individual API keys — outside governance, outside audit, outside POPIA compliance. This is a CISO risk that compounds monthly.
🔴 LLM cost fragmentation
Each division procuring separate LLM API contracts results in MTN paying 3–8x what centralised negotiation would achieve. No visibility into aggregate token spend or cost-per-division attribution.

Desired Future State

A self-service internal platform where a Fintech BA, a Network operations analyst, or an HR manager can log in with their Azure AD credentials, browse a library of pre-approved agent templates, customise one for their workflow, submit it through an approval gate, and have it live — governed, audited, cost-attributed — within days rather than months.

Scope & Functional Requirements

3.1 Agent Template Library

MUST  FR-01: The platform MUST provide a pre-built template library of at least 42 agent templates covering all 8 major MTN division categories (Fintech, Network, Legal, HR, Finance, Customer Care, Marketing, IT).
MUST  FR-02: Templates MUST be filterable by division, category, complexity tier and compliance tag (POPIA, ISO27001, SOC2).
MUST  FR-03: Each template MUST include a pre-wired tool set, retry policy, timeout configuration, and default input/output schema.
SHOULD  FR-04: Templates SHOULD display estimated LLM token cost per execution and typical latency before deployment.

3.2 Visual Workflow Builder (DAG)

MUST  FR-05: The platform MUST provide a drag-and-drop DAG workflow builder allowing users to chain multiple agents into multi-step workflows with conditional routing and parallel fan-out.
MUST  FR-06: The workflow engine MUST perform cycle detection (topological sort) and reject circular dependency configurations before saving.
MUST  FR-07: Each workflow node MUST support configurable timeout, retry policy (max retries, backoff multiplier) and failure routing (fail-fast vs. skip-and-continue).
MUST  FR-08: Workflow execution state MUST be persisted in PostgreSQL — not held in memory — so execution survives pod restarts and horizontal scaling.
SHOULD  FR-09: The workflow builder SHOULD provide a live simulation mode allowing stakeholders to step through execution with synthetic data before production deployment.

3.3 Approval Gates

MUST  FR-10: All new agent deployments MUST pass through a configurable approval gate — minimum: division lead approval. High-risk agents (financial actions, PII access) MUST additionally require CISO sign-off.
MUST  FR-11: Approval gates MUST display: agent name, division, risk tier, tools requested, data access scope, estimated monthly cost, and compliance tags.
MUST  FR-12: Approved/rejected status MUST be immutably written to the audit trail with approver identity, timestamp and justification notes.

3.4 Multi-Division RBAC

MUST  FR-13: The platform MUST enforce row-level division isolation — agents, workflows and data created by Fintech are not visible to Network, and vice versa, unless explicitly shared.
MUST  FR-14: Roles MUST include: Platform Admin (cross-division), Division Owner (own division), Agent Developer (own division, no deploy), Viewer (read-only).
MUST  FR-15: Authentication MUST integrate with MTN Azure Active Directory via OAuth 2.0 / OIDC. All user provisioning flows through existing Azure AD groups.

3.5 Audit Trail & Observability

MUST  FR-16: Every agent execution MUST produce an immutable audit log entry capturing: execution ID, agent ID, division, user/trigger, input hash, output hash, tokens used, cost USD, latency ms, and pass/fail status.
MUST  FR-17: Audit logs MUST be queryable by division, date range, agent, and status. Export to CSV MUST be available for compliance reporting.
SHOULD  FR-18: The platform SHOULD integrate with MTN's Pulse observability stack (UC-17) to surface agent execution traces in the existing APM dashboard.

3.6 LLM Gateway & Cost Attribution

MUST  FR-19: All LLM calls MUST route through a centralised LLM Gateway that enforces rate limits, provides failover between providers (Azure OpenAI primary, Anthropic fallback), and attributes token spend per division.
MUST  FR-20: Monthly cost attribution per division MUST be visible to Platform Admins and Division Owners, enabling internal showback/chargeback.

3.7 Integration Hub

MUST  FR-21: Pre-built connectors MUST be available for: MTN MoMo API, Azure AD, Microsoft Teams, ServiceNow, Pulse Observability, SharePoint, SAP HR, Oracle Financials.
SHOULD  FR-22: A generic REST connector MUST allow any division to wire up custom internal APIs with OAuth 2.0 or API key authentication, without platform code changes.

User Stories

Platform Admin

US-01 · Platform Admin
"As a Platform Admin, I want to see all agents deployed across all 16 divisions with their status, token spend, and approval state — so I can manage the platform holistically and identify rogue or costly deployments."
Acceptance Criteria: Cross-division agent list with search/filter by division, status, cost tier; sortable by monthly spend; exportable to CSV.
US-02 · Platform Admin
"As a Platform Admin, I want to configure and publish new agent templates to the shared library — so divisions can self-serve without waiting for engineering."
Acceptance Criteria: Template creation form with schema editor, tool assignment, compliance tag picker, preview before publish; publish triggers division notification.

Division Owner

US-03 · Division Owner (e.g. Fintech)
"As a Fintech Division Owner, I want to approve or reject agent deployment requests from my team — so I maintain control over what automation runs within my division."
Acceptance Criteria: Approval queue showing agent details, risk tier, tools, data scope, estimated cost; one-click approve/reject with optional notes; decision recorded immutably in audit trail.
US-04 · Division Owner
"As a Division Owner, I want to see my division's monthly LLM spend broken down by agent — so I can hold teams accountable and manage the AI budget."
Acceptance Criteria: Division cost dashboard with per-agent breakdown, month-to-date and last-3-month trend; projected monthly spend alert at 80% of budget.

Agent Developer (BA / Analyst)

US-05 · Agent Developer
"As a Fintech BA, I want to browse the template library, find a document processing agent, clone it and configure it for our KYC workflow — without writing any code."
Acceptance Criteria: Template search with division/category filter; clone creates a draft in my division; configuration form pre-populated from template; submit for approval with one click.
US-06 · Agent Developer
"As a Network Ops analyst, I want to build a multi-agent workflow that detects anomalies, runs a root cause analysis agent, and then posts a summary to Teams — all triggered automatically by a network event."
Acceptance Criteria: Visual DAG builder with 3-node workflow; event trigger configuration; Teams connector with message template; workflow simulation before submit; audit log shows each node's execution.
US-07 · Agent Developer
"As an HR analyst, I want to see why my onboarding agent failed last Tuesday — so I can debug it without needing to escalate to engineering."
Acceptance Criteria: Execution history for my agents with per-node status, error message, input/output preview, and retry option; accessible to developer role without Platform Admin privileges.

Viewer

US-08 · Viewer (e.g. Finance Controller)
"As a Finance Controller, I want read-only visibility into AI agent activity in my division — so I can reconcile AI spend in the monthly cost report."
Acceptance Criteria: Read-only dashboard access to division agents, execution count, token cost, approval status; no ability to create, edit or trigger agents.

CISO / Compliance

US-09 · CISO
"As the MTN CISO, I want to be in the approval chain for any agent that accesses PII, financial transaction data, or makes external API calls — so I can enforce our data governance policy."
Acceptance Criteria: Agents tagged HIGH_RISK or PII_ACCESS automatically route to CISO approval queue; CISO sees agent data access scope, tools, network egress endpoints; approval or rejection with mandatory written justification.

Key Architectural Changes from Swifter Base

🔧 In-memory state → PostgreSQL-persisted workflows
The Swifter OrchestrationEngine held workflow state in a Map<string, Workflow> singleton — lost on every pod restart. MTN implementation writes workflow state to PostgreSQL on every node transition, enabling true horizontal scale and pod-resilient execution.
🔧 In-memory AgentMemory → pgvector
InMemoryAgentMemory replaced with PostgreSQL + pgvector for semantic memory queries. Supports similarity search across agent execution history for context-aware agents.
🔧 Tenant model → Division model
Swifter's generic tenantId maps to MTN's 16-division structure. Division metadata (name, market, RBAC group, budget cap) is stored in a divisions table with Azure AD group binding.
🔧 Generic RBAC → MTN role taxonomy
Platform Admin, Division Owner, Agent Developer, Viewer roles mapped to Azure AD security groups. CISO role added for high-risk approval gate.

Compliance & Security Requirements

POPIA (South Africa)

  • All PII fields processed by agents MUST be identified, tagged, and encrypted at rest with AES-256
  • Agent execution logs MUST NOT store raw PII — SHA-256 hashed references only
  • Data subject access requests for agent-processed data MUST be fulfillable within 72 hours
  • PII-touching agents MUST appear in the POPIA processing register auto-generated by the platform

ISO 27001

  • Access control logs (logins, approvals, config changes) MUST be retained for minimum 1 year
  • Platform MUST support quarterly access review export for ISO 27001 Annex A.9 controls
  • Penetration test required before production launch; findings tracked to closure

CISO Approval Gate

⚠️ Mandatory CISO Review: Agents with any of the following properties MUST route to the CISO approval queue before activation: tool access to payment APIs, PII field processing, external network egress beyond the approved integration whitelist, execution of financial transactions, or bulk data export capabilities.
