Problem Statement

Complex multi-step operations on the fintech platform — such as merchant onboarding, compliance configuration, payment limit adjustments, and API key provisioning — require engineers and operations staff to manually chain together multiple API calls across different systems. This process is:

Time-Consuming and Error-Prone
A typical merchant onboarding workflow involves 8–12 API calls across 3 systems. Manual execution takes 30–90 minutes and is prone to errors when steps are executed out of sequence or with incorrect parameters.
Requires Deep Technical Knowledge
Operations staff without deep API knowledge cannot execute these workflows independently. Every complex task requires a developer. This creates bottlenecks and reduces operational agility.
No Audit Trail for Composite Operations
When a multi-step operation partially fails, there is no centralised record of what succeeded and what failed. Recovery requires manual investigation across multiple system logs.
Undocumented Tribal Knowledge
The correct sequence and parameters for complex workflows exist only in experienced engineers' heads or in informal Confluence pages. New team members cannot safely execute these operations without guidance.

Personas & Stakeholders

Primary Users

Operations Engineer (Primary)
Executes platform configuration and onboarding tasks daily. Technical but not a software developer. Wants to describe what they need in plain language and have the system figure out the right API sequence. Needs confidence that irreversible actions won't execute without their explicit approval.
Platform Engineer / Developer
Builds and maintains the internal APIs. Will use the orchestration agent for complex debugging and configuration tasks. Comfortable with API call details — wants to review and edit the generated plan before execution. Needs the audit log for post-incident investigation.

Secondary Stakeholders

Head of Engineering (Malcolm Govender)
Cares about reduction in developer interruptions for ops tasks, audit trail completeness, and POPIA compliance. Will sign off on production go-live.
CISO
Deeply concerned about an AI agent that can execute write operations on production systems. Requires threat model, privilege control documentation, and approval gate design before any testing on non-dev environments.

User Stories

⚠ Pre-build requirement: Before any user stories can be implemented, the approval gate policy and tool registry risk classification must be completed and signed off by the CISO. No write-enabled tools should be accessible to the agent without this framework in place.

Epic 1: Natural Language Task Orchestration

US-19-01 MUST
"As an operations engineer, I want to describe a platform task in plain English and have the agent generate a step-by-step execution plan that I can review before anything runs, so I can safely perform complex workflows without knowing the exact API calls."
Acceptance Criteria:
  • Agent accepts natural language task description via web UI
  • Step planner generates ordered plan with: step name, API to call, parameters, expected outcome, risk level
  • Plan displayed for user review before any execution begins
  • User can edit individual step parameters before approving
  • Plan generation completes within 15 seconds
US-19-02 MUST
"As an operations engineer, I want the agent to pause and ask for my explicit approval before executing any step that creates, modifies, or deletes data, so I am always in control of irreversible actions."
Acceptance Criteria:
  • All steps classified as WRITE, DELETE, or READ at plan generation time
  • WRITE and DELETE steps require explicit user approval before execution
  • Approval UI shows: what will be called, with what parameters, what the expected side effect is
  • User can cancel at any approval gate without partial execution side effects (or with clear rollback guidance)
US-19-03 MUST
"As an operations engineer, I want to see a real-time execution log as the agent runs each step, so I know what is happening and can intervene if something looks wrong."
Acceptance Criteria:
  • Each step shows: status (pending / running / success / failed), API called, response summary
  • Step results update in real-time without page refresh
  • Execution can be paused or aborted by the user at any point
  • Final execution summary shows: total steps, successful, failed, time taken
US-19-04 MUST
"As an operations engineer, I want the agent to automatically retry failed steps with the correct parameters, and tell me clearly when a failure requires manual intervention, so I don't have to restart entire workflows from scratch."
Acceptance Criteria:
  • Transient failures (network timeouts, rate limits) auto-retried up to 3 times with exponential back-off
  • Permanent failures (validation errors, auth failures) surfaced immediately with clear error message and suggested resolution
  • Successfully completed steps are not re-run on retry
  • User can resume from last successful step after resolving a failure
US-19-05 MUST
"As a compliance officer, I want every orchestration execution to be fully logged with the actor, all API calls made, parameters sent, and responses received, so we have a complete audit trail for regulatory purposes."
Acceptance Criteria:
  • Immutable audit log entry created for every orchestration execution
  • Log includes: actor (user identity), task description, plan generated, each step executed, API endpoint, request payload (PII redacted), response status, timestamp
  • Logs retained for minimum 12 months
  • Logs queryable by actor, date range, workflow type
  • Log cannot be modified or deleted by any user (including admins)
US-19-06 SHOULD
"As an operations engineer, I want to save common workflow templates so I can re-run standard operations (e.g., standard merchant onboarding) with just a few parameter inputs, without re-describing the full workflow each time."
Acceptance Criteria:
  • Any executed workflow can be saved as a named template
  • Template stores: workflow name, step structure, input parameter schema
  • Template can be triggered with only variable parameters as input
  • Templates can be shared across team (or kept private)
US-19-07 SHOULD
"As a platform engineer, I want to run the orchestration agent in dry-run mode where all API calls are simulated and no real changes are made, so I can validate complex plans safely before executing on production."
Acceptance Criteria:
  • Dry-run mode clearly indicated in UI (cannot be confused with real execution)
  • All API calls simulated against mock responses or staging environment
  • Dry-run report shows what would have been called and expected outcomes
  • Dry-run results can be converted to a real execution with one action
US-19-08 NICE TO HAVE
"As an operations engineer, I want the agent to suggest the most relevant workflow template when I describe a task, rather than always generating a plan from scratch, so common operations are fast and consistent."
Acceptance Criteria:
  • Agent matches user description to existing templates using semantic similarity
  • Top 3 matching templates offered before plan generation starts
  • User can select a template or continue with fresh plan generation

Technical Dependencies

Azure OpenAI — GPT-4o (Structured Output / Tool Use)
Required for step planner and tool selection. Must use structured output mode with JSON schema enforcement for reliable plan generation. Azure South Africa North deployment required for data residency compliance.
Internal API Inventory & OpenAPI Specs
The tool registry can only be built once all internal APIs are documented with OpenAPI specs. This is a Sprint 0 dependency — Artemij must compile the full API inventory before Sprint 1 begins.
OAuth 2.0 Identity Provider
The agent must obtain and forward the caller's OAuth token to each downstream API. Requires identity provider integration (Azure AD / Entra ID) and token forwarding mechanism in execution engine.
Persistent State Store
Execution state must be persisted to survive restarts. Recommend Azure Cosmos DB or PostgreSQL for state storage. Schema must support: execution ID, step states, intermediate outputs, and actor identity.
Immutable Audit Log Store
Audit logs require a write-once, tamper-evident store. Options: Azure Immutable Blob Storage, Azure Monitor Logs with retention lock, or a dedicated append-only database table. Legal sign-off on storage approach required.
CISO Approval — Threat Model & Risk Framework
Non-negotiable: CISO must review and approve the threat model, approval gate policy, and privilege control design before any code is written for production-facing components. This is a blocker for Sprint 1.

Definition of Done — Full Acceptance Criteria

  • CISO threat model review completed and approved prior to Sprint 1 start
  • Tool registry compiled with all internal APIs, risk classifications, and OpenAPI schemas
  • Step planner generates correct execution plans for ≥ 15 documented workflow scenarios
  • Approval gateway tested: no WRITE or DELETE step executes without explicit user confirmation in any test scenario
  • Execution engine handles sequential steps, output passing, and retry correctly across all test scenarios
  • Failed executions resumable from last successful step within 24 hours of failure
  • All API calls execute using caller OAuth token — confirmed via penetration test that no privilege escalation is possible
  • Audit log captures complete execution trace; PII fields redacted per POPIA; logs retained for 12 months
  • Dry-run mode validated: zero real API calls made during dry-run execution in all test cases
  • Integration test suite passing on ≥ 15 workflow scenarios including error paths and approval gate flows
  • Head of Engineering and CISO production sign-off obtained
  • 4-week shadow-mode completed — parallel manual process comparison; MTTR/time-savings validated
  • On-call runbook published; escalation path documented for stuck/failed orchestrations
