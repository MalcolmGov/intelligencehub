Problem Statement

Manual test case creation from user stories, business requirements documents (BRDs), and API specifications is time-consuming, error-prone, and difficult to scale across multiple projects. QA engineers spend 40-60% of their time translating requirements into structured test steps rather than executing tests or analyzing results.

Current workflows require:

  • Manual parsing of natural language requirements to extract testable scenarios
  • Duplicate effort when similar features or APIs are tested across projects
  • Limited traceability between requirements and test cases, making compliance audits challenging
  • No automated connection between API documentation (Swagger/OpenAPI) and test coverage

For SentinelQA and fintech QA, this inefficiency translates to slower release cycles, incomplete test coverage for regulatory-critical features, and missed edge cases in payment processing and compliance workflows.

Goals: Generate test cases quickly from requirements, maintain high test coverage, reduce manual test writing time by 50%

Role: Team lead overseeing test strategy and quality metrics
Goals: Improve team velocity, ensure comprehensive test coverage, maintain audit trails for compliance, scale testing to new projects
Frustrations: Gaps in coverage for edge cases; inconsistent test case naming and structure; difficulty tracking which requirements are tested; onboarding new engineers takes weeks
3. Dr. Priya Patel – Product Manager
Role: PM writing complex feature requirements and BRDs
Goals: See requirements instantly converted to test cases, ensure feature intent is captured in tests, reduce back-and-forth with QA

User Stories

US-01
As a QA engineer, I want to upload a user story in plain English and have the system generate 5-10 structured test cases with steps, expected results, and data requirements, so that I can reduce manual test case creation time from 2 hours to 15 minutes per story.
Must Have
US-02
As a dev integration lead, I want to upload an OpenAPI/Swagger spec and have the system generate test cases for all endpoints (GET, POST, PUT, DELETE) with valid/invalid payloads, authentication tests, and error scenarios, so that API coverage increases from 60% to 95%.
Must Have
US-03
As a QA lead, I want generated test cases to include traceability links back to source requirements (story ID, BRD section), so that I can audit which requirements are covered in tests for compliance sign-offs.
Must Have
US-04
As a QA engineer, I want generated test cases to be pushed to GitHub as draft pull requests with clear commit messages, so that I can review, edit, and merge them into my test suite without manual file creation.
Must Have
US-05
As a QA engineer, I want the system to detect and flag duplicate test cases (same scenario, different wording) and suggest merging them, so that test suite remains lean and maintainable.
Should Have
US-06
As a product manager, I want to view generated test cases grouped by feature and see coverage percentage per requirement, so that I understand test completeness before handoff to QA.
Should Have
US-07
As a QA engineer, I want the system to suggest test data fixtures (sample payment amounts, user IDs, timestamps) based on API schemas and domain context, so that tests run immediately without manual fixture creation.
Should Have
US-08
As a QA lead, I want to define reusable test templates for common scenarios (login flow, payment processing, error handling), so that generated test cases follow consistent patterns across projects.
Nice to Have
US-09
As a QA engineer, I want the system to analyze requirements for potential edge cases (boundary values, null inputs, race conditions) and auto-generate test cases for them, so that test coverage improves beyond happy-path scenarios.

Functional Requirements

FR-01Accept plain-English user stories (free text, up to 2000 chars) and parse them into structured test scenarios with pre/post conditions and edge case detection.
FR-02Accept OpenAPI 3.0 / Swagger 2.0 specifications and auto-generate test cases for all operations, covering request/response validation, authentication, rate limits, and error codes.
FR-03Generate test cases in industry-standard format: Gherkin (BDD), Test Case ID, Steps, Expected Results, Pre-conditions, Post-conditions, Data Requirements.
FR-04Link generated test cases to source requirements via unique IDs, with bidirectional traceability matrix export (CSV/JSON).
FR-05Create GitHub draft pull requests with generated test cases, allowing QA to review, edit comments, and merge into target branch (feature branch or main).
FR-06Detect semantic duplicates in generated test cases using NLP, highlight them to QA for manual merge decision.
FR-07Support multi-language requirements input (English, Spanish, French) with automatic translation to English for processing.
FR-08Generate parameterised test data fixtures with realistic values (payment amounts 0.01–9999.99, valid IBAN/BIC, valid email formats, timestamp ranges).
FR-09Expose coverage dashboard: % of requirements with generated test cases, test count per feature, high-risk untested areas flagged in red.
FR-10Support batch import: accept ZIP of 50+ BRD files (PDF/Word) and generate test cases for all in one job (async, with email notification on completion).
FR-11Allow QA engineers to edit AI-generated test case steps, mark as approved/rejected, and use feedback to improve future generations.
FR-12Export generated test cases in Playwright, Cypress, Jest, and Pytest formats with syntax-ready structure.
FR-13Maintain version history of generated test cases, tracking changes and allowing rollback to previous versions.
FR-14Integrate with SentinelQA Test Studio: generated test cases appear in test inventory with origin metadata and status.
FR-15Support customizable test case templates per project with pre-defined mandatory fields, naming conventions, and assertion styles.

Non-Functional Requirements

NFR-01Performance: Generate 10 test cases from a user story in <2 seconds; process OpenAPI spec with 50+ endpoints in <5 seconds.
NFR-02Scalability: Support concurrent generation jobs for 100+ users; handle batch imports of 500+ requirements without degradation.
NFR-03Security: Encrypt all requirements data in transit and at rest; sanitise output to prevent injection attacks in generated test code; enforce RBAC for viewing sensitive requirements.
NFR-04Reliability: 99.5% uptime SLA; automatic retry on API timeouts; graceful degradation if GitHub API is unavailable (queue PRs for later submission).
NFR-05Observability: Log all generation requests with input/output tokens, latency, model version; export metrics to CloudWatch; surface errors to QA dashboard.
NFR-06Compliance: Maintain audit logs of all test case generation (who, when, source requirement, output); support GDPR data deletion of sensitive inputs.
NFR-07Usability: Test case generation interface must be self-explanatory; support drag-drop file upload and progress tracking; no CLI required for QA engineers.
NFR-08Maintainability: AI model updates should not break existing test case structure; semantic versioning for API responses; rollback capability for model changes.

Acceptance Criteria

Feature: User Story → Test Case Generation

Given a valid user story input, when the QA engineer submits it, then the system generates 5-10 test cases within 2 seconds with Gherkin format, unique test IDs, and pre/post conditions.
Given a user story with ambiguous language, when processed, then the system flags uncertainty and asks clarifying questions before finalising test cases (e.g., "Which login method: password or SSO?").
Given a user story with edge case mentions (e.g., "handle invalid input"), when processed, then test cases include explicit negative test cases for the mentioned edge cases.

Feature: OpenAPI → Test Case Generation

Given a valid OpenAPI 3.0 spec with 20 endpoints, when uploaded, then the system generates at least 2 test cases per endpoint (happy path + error path) within 5 seconds.
Given an endpoint with authentication (Bearer token, OAuth), when processed, then generated test cases include both authenticated and unauthenticated requests with expected 401/403 responses.
Given a request schema with required vs optional fields, when processed, then test cases validate both required field presence and optional field omission.

Feature: GitHub PR Creation

Given generated test cases, when the QA engineer selects "Create PR", then a draft PR is created on the specified GitHub branch with test cases as .spec files, a clear commit message, and PR description linking to source requirement.
Given a batch of 50 test cases, when pushed to GitHub, then all cases are in a single PR with organised folder structure matching project conventions.

Feature: Traceability

Given a requirement ID (e.g., STORY-123), when exported, then traceability matrix shows all test cases linking to that requirement with coverage percentage.
Given a test case, when viewed, then it displays the source requirement, user story text, generation timestamp, and approval status.

Dependencies & Integrations

SentinelQA Test Studio (Internal): Generated test cases are stored in Test Studio database; requires REST API integration for CRUD operations on test_case table. Status: Existing integration.
GitHub API: For draft PR creation, branch listing, commit operations. Uses GitHub App authentication (OAuth). Status: Existing integration.
OpenAPI Parser Library: To validate and parse OpenAPI 3.0/Swagger 2.0 specs. Recommendation: use 'openapi3' npm package or Python 'openapi-spec-validator'. Status: To be integrated.
AI Language Model (Claude 3.5 Sonnet or GPT-4): For requirement parsing, test case generation, edge case detection. Requires token-based API calls with retry logic. Status: Existing integration (Test Studio already uses Claude).
NLP Duplicate Detection: To identify semantic duplicates. Recommendation: use 'sentence-transformers' library for embeddings + cosine similarity. Status: To be integrated.
Gherkin/BDD Formatter: To convert AI-generated test descriptions to Gherkin syntax. Recommendation: 'gherkin-formatter' or custom Handlebars templates. Status: To be integrated.
PDF/Word Parser (for BRD batch import): To extract text from uploaded BRD files. Recommendation: 'pdf-parse' (Node.js) and 'mammoth' (Word docs). Status: To be integrated.
CloudWatch / DataDog: For logging, metrics, and alert thresholds on generation failures. Status: Existing infrastructure.

Assumptions & Constraints

Assumptions

  • Requirements are written in clear, moderately-detailed English (minimum 50 words); vague 1-line stories will produce lower-quality test cases.
  • QA engineers have GitHub access and familiarity with pull request workflows.
  • OpenAPI specs are well-formed and describe actual API behaviour (not aspirational specs).
  • Generated test cases will be reviewed and refined by humans; AI output is a starting point, not production-ready without QA approval.
  • Fintech domain context is provided via project templates and custom rules, not inferred from requirements alone.

Constraints

  • Regulation (PCI-DSS, FICA): Generated test cases must not include actual payment card numbers, customer PII, or sensitive financial data; fixtures use synthetic/masked data only.
  • AI Model Cost: Each generation request consumes tokens; must implement caching and rate limiting to control costs.
  • Latency: Real-time generation is acceptable up to 5 seconds; batch jobs (500+ cases) will be async with email notification.
  • Test Coverage Gap: AI-generated test cases supplement human-written tests; edge cases and domain-specific logic still require manual test case creation.
  • GitHub API Rate Limit: 5000 requests/hour per GitHub App; batch PR creation must respect this limit with queuing.
  • Supported Languages: v1 supports English requirements only; multi-language support planned for v1.1.

Out of Scope (v1.0)

Test case execution / test result analysis (handled by Test Runner, not this module).
Automatic merge of generated test cases into main branch (QA must review and approve via PR).
Code coverage analysis or mutation testing.
Conversion of existing manual test cases to AI-generated format (data migration tool planned for v1.1).
Custom test frameworks beyond Playwright, Cypress, Jest, Pytest (e.g., Selenium, TestCafe).
Real-time bi-directional sync between requirements documents and generated test cases (one-way generation only in v1).
Support for requirements in non-English languages (v1.0 only accepts English input).
Integration with enterprise ALM tools (Azure DevOps, Jira) beyond basic traceability links.

Definition of Done

  • User stories from all 3 personas tested and validated in UAT environment
  • All functional requirements (FR-01 to FR-15) implemented and unit-tested with >90% code coverage
  • All non-functional requirements (NFR-01 to NFR-08) verified via load testing, security audit, and chaos engineering tests
  • Integration tests confirm end-to-end flow: BRD upload → test case generation → GitHub PR creation → SentinelQA ingestion
  • API documentation (OpenAPI spec) for test case generation endpoints published
  • User documentation (screenshots, video walkthrough) created for QA engineers and PMs
  • Error handling for all edge cases: invalid file formats, API timeouts, GitHub auth failures, quota limits
  • Security review completed: no PII/payment data leakage, input sanitisation verified, RBAC enforced
  • Performance testing: 2s generation time for 10 test cases, <5s for 50-endpoint OpenAPI specs validated
  • Accessibility audit: dark theme meets WCAG 2.1 AA contrast ratios; keyboard navigation functional
  • Cost analysis: token usage per operation documented; cost optimisation recommendations provided
  • Production deployment checklist: database migrations, feature flags, monitoring alerts, rollback plan
  • Stakeholder sign-off: Malcolm Govender (Head of AI & Engineering), product manager, and QA lead approval recorded
