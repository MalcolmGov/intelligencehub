Problem Statement

When incidents occur in production, on-call engineers face an overwhelming flood of correlated alerts without clear diagnosis. They must manually sift through logs, metrics, traces, and recent deployments to identify root causes — a process that takes 20–60 minutes on average. This extended MTTR has direct financial impact (payment processing downtime costs thousands per minute), increases engineer burnout, and risks cascading failures.

Key pain points:

Alert Storm Overload
A single infrastructure failure triggers 50–200 secondary alerts. Engineers struggle to identify the causal root alert from the noise, wasting critical time.
Manual Deployment Correlation
Engineers must manually cross-reference incident timing with recent deployments from the CI/CD system. This correlation is the most common root cause but currently requires checking multiple systems.
Institutional Knowledge Loss
Resolved incidents are documented in Confluence or PagerDuty postmortems but are rarely searched during active incidents. Tribal knowledge exists only in experienced engineers' heads.
No Anomaly Baseline
Without statistical baselines, teams cannot distinguish genuine anomalies from normal variance — resulting in both false-positive pages and missed real issues.

Personas & Stakeholders

Primary Users

On-Call Engineer (Primary)
Woken at 2am by a P1 alert. Needs to identify and resolve the root cause as fast as possible. Time-pressured, high-stress, may not have full system context. Wants clear, actionable RCA output — not a wall of logs.
Incident Commander
Coordinates multi-team incident response. Needs a high-level AI ops brief they can share with stakeholders without deep technical knowledge. Communicates to leadership and customers.
SRE / Platform Engineer
Reviews incident patterns over time. Uses RCA history to identify systemic issues and drive reliability improvements. Needs corpus search and trend analytics.

Secondary Stakeholders

Head of Engineering / CTO
Cares about MTTR reduction, SLA adherence, and incident volume trends. Reviews monthly reliability reports.
CISO
Needs audit trail of all incidents and RCA outputs. Concerned with data sovereignty — LLM calls must not leak production data outside approved boundaries.

User Stories

Epic 1: Real-Time RCA During Incidents

US-17-01 MUST
"As an on-call engineer, I want the system to automatically correlate all active alerts into a single root cause hypothesis within 30 seconds of incident declaration, so I can start remediation immediately rather than spending 20 minutes on manual triage."
Acceptance Criteria:
  • RCA engine activates automatically on P1/P2 incident declaration in PagerDuty
  • Output includes: probable root cause, confidence %, affected services, recommended remediation steps
  • First RCA result delivered within 30 seconds of incident trigger
  • Results visible in Pulse incident command view
US-17-02 MUST
"As an on-call engineer, I want the RCA to automatically surface any deployments in the 2 hours before the incident, so I can quickly assess whether a code change caused the issue."
Acceptance Criteria:
  • System ingests deployment events from Azure DevOps / GitHub Actions via webhook
  • Recent deployments (last 2 hours) displayed in incident command view timeline
  • If deployment-to-incident correlation detected, prominently flagged in RCA output
US-17-03 MUST
"As an incident commander, I want a plain-English AI ops brief that summarises what is happening, what the likely cause is, and what teams are needed, so I can communicate status without needing to interpret raw telemetry."
Acceptance Criteria:
  • AI ops brief generated automatically; max 200 words, non-technical language
  • Includes: impact summary, probable cause, affected teams, recommended escalation path
  • Copyable to clipboard for Slack/email with one click
US-17-04 SHOULD
"As an on-call engineer, I want to see whether this incident pattern has occurred before, with links to the postmortem and the fix that resolved it, so I can apply the same fix immediately."
Acceptance Criteria:
  • Historical incident corpus queried using semantic similarity on alert signals
  • Top 3 similar past incidents surfaced with similarity score
  • Link to original postmortem / resolution notes included
US-17-05 SHOULD
"As an SRE, I want the system to alert me when a service metric deviates statistically from its baseline, before it triggers a user-facing incident, so we can intervene proactively."
Acceptance Criteria:
  • ML anomaly detection model trained on 30+ days of metric time-series
  • Anomaly score surfaced in Pulse dashboard with deviation magnitude
  • Early warning alert generated for anomalies above configurable threshold
  • False positive rate < 5% on validation dataset
US-17-06 NICE TO HAVE
"As an SRE, I want resolved incidents to automatically be embedded and added to the knowledge corpus, so the system gets smarter with every incident we resolve."
Acceptance Criteria:
  • On incident resolution, system extracts: root cause, resolution steps, duration, affected services
  • Embeds and stores in vector store automatically (no manual action)
  • New incident data available for similarity search within 5 minutes of resolution
US-17-07 NICE TO HAVE
"As an on-call engineer, I want ITSM tickets (ServiceNow) to be automatically created and linked to the Pulse incident, so I don't need to context-switch during active triage."
Acceptance Criteria:
  • P1/P2 incidents auto-create ServiceNow tickets with AI-populated description
  • Ticket includes link back to Pulse incident command view
  • CMDB CI (configuration item) auto-populated from service registry

Epic 2: Post-Incident Learning

US-17-08 MUST
"As an SRE, I want to rate the quality of each RCA output (thumbs up/down) so we can track accuracy over time and identify where the model needs improvement."
Acceptance Criteria:
  • RCA output has thumbs up/down rating in Pulse UI
  • Rating stored with incident record
  • Monthly RCA accuracy report available (% rated correct)

Technical Dependencies

Azure OpenAI (GPT-4o)
Required for RCA reasoning and AI ops brief generation. Must be provisioned in Azure South Africa North. Requires CISO approval for production data processing.
PagerDuty — Webhook Integration
Incident lifecycle events (triggered, acknowledged, resolved) must be forwarded to Pulse webhook endpoint. Requires PagerDuty admin access to configure webhooks.
Prometheus / Grafana
Metric time-series data required for anomaly detection and alert correlation. Pulse must be able to query Prometheus remote_write endpoint or use direct API query.
Azure DevOps / GitHub Actions — Deployment Webhooks
CI/CD pipelines must send deployment events (service, version, timestamp, environment) to Pulse ingestion endpoint on successful deployment. Required for deployment-incident correlation.
Azure AI Search (Vector Store)
Historical incident corpus requires a vector store supporting semantic similarity search. Azure AI Search (index with embedding field) is the recommended choice within the existing Azure footprint.
ServiceNow — ITSM (Phase 2)
CMDB and ticket creation integration. Requires ServiceNow admin to provision OAuth client credentials and share CMDB service topology export. Phase 2 dependency.

Definition of Done — Full Acceptance Criteria

  • RCA engine correctly identifies root cause in ≥ 80% of test incident scenarios
  • First RCA output delivered within 30 seconds of P1 incident trigger
  • Incident command view shows alert timeline, RCA output, AI ops brief in single view
  • Deployment event ingestion live and tested end-to-end with Azure DevOps
  • ML anomaly detection model trained and validating at < 5% false positive rate
  • Historical incident corpus seeded with ≥ 50 past incidents; semantic search returning relevant matches
  • On-call runbook published to Confluence covering: how to use Pulse RCA, how to rate RCA quality, how to escalate when RCA is wrong
  • Integration test suite passing with ≥ 90% coverage of critical signal paths
  • 2-week shadow-mode run completed — RCA output compared against manual triage; accuracy report approved by Head of Engineering
  • CISO sign-off on data residency controls (no production PII to OpenAI US endpoints)
