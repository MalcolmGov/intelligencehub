Problem Statement

Automated tests are brittle: when UI elements change—CSS class names are updated, IDs are modified, elements are relocated—tests fail immediately. Teams spend 20–30% of their time maintaining and fixing broken selectors rather than improving test coverage or writing new tests.

Current pain points:

  • Minor CSS changes break 50+ tests; manual selector updates required across multiple files
  • Tests fail on layout refactors even though functionality is unchanged
  • No visibility into which selectors are fragile; maintenance becomes reactive
  • Teams must choose between aggressive retry logic (masking real failures) or frequent test flakiness
  • Mobile UI changes (responsive layouts) cause cascading selector failures

Self-healing automation uses AI, semantic matching, and computer vision to autonomously repair broken selectors, dramatically reducing maintenance burden and increasing test reliability. For SentinelQA fintech customers, this translates to faster feature releases, fewer false-positive test failures, and more time for exploratory testing.

Functional Requirements

FR-28Monitor all test executions; when a selector fails (element not found), capture the page screenshot and DOM context (HTML source, CSS state).
FR-29Implement multi-strategy selector recovery: (1) Semantic matching on ARIA labels, placeholders, alt text; (2) Computer vision to locate similar-looking elements; (3) Fallback XPath with regex; (4) Parent/sibling structural matching.
FR-30When a repair is found, either auto-apply (if confidence > 95%) or queue for human approval (if confidence 70–95%); log confidence score and recovery method.
FR-31Provide a "Selector Repairs" dashboard showing all repaired selectors with before/after, confidence, recovery method, and approval status.
FR-32Generate pull requests with repaired selectors, including: old/new selectors side-by-side, test file line references, confidence score, recovery method in comment.
FR-33Track selector fragility over time: flag selectors that change frequently, fail repairs multiple times, or are device-dependent.
FR-34Support adaptive selectors for responsive design: device-aware locators that adjust XPath/CSS based on screen size or device type.
FR-35Integrate with SentinelQA test runner: intercept selector failures, trigger healing logic, retry test with healed selector automatically.
FR-36Provide CSS change impact analysis: when a CSS file changes, estimate which tests may be affected and suggest proactive repairs.
FR-37Store repair history per selector: all historical repairs, success rates, and recommend "best" selector based on stability.
FR-38Support explicit selector repair approval workflow: QA can review and approve/reject repairs in dashboard before auto-commit to GitHub.
FR-39Generate metrics: % of tests with auto-healed selectors, success rate of repairs, reduction in manual selector maintenance time.

Non-Functional Requirements

Acceptance Criteria

Feature: Autonomous Selector Repair

Given a test fails with "element not found" for a button with original selector #submit-btn, when the page has changed and the button now has class submit-primary, then the system finds the button via semantic matching (still a submit button) and suggests the new selector with >90% confidence.
Given a high-confidence repair (>95%), when auto-applied, then the test is automatically retried with the new selector and passes.
Given a medium-confidence repair (75–85%), when queued for approval, then it appears in the Selector Repairs dashboard with confidence score, recovery method, and side-by-side comparison.

Feature: Repair Dashboard

Given 50 repaired selectors, when viewing the dashboard, then all repairs are listed with before/after, confidence, recovery method, and approval status; filters for device type, urgency, and confidence range are functional.
Given a QA engineer viewing a repair, when clicking "Approve," then the repair is committed to GitHub as a PR with explanation comment; when clicking "Reject," the repair is discarded and logged.

Feature: Fragility Detection

Given a selector that has been repaired 5+ times in the last month, when viewed in the dashboard, then it is flagged as "fragile" with recommendation to refactor the underlying element.

Feature: GitHub PR Creation

Given 10 approved repairs, when "Create PR" is selected, then a single draft PR is created with all repairs, organized by file, with clear commit message linking to original test files and confidence scores in comments.

Assumptions & Constraints

Assumptions

  • Page DOM structure remains logically similar after UI changes; element semantic properties (buttons are still buttons, inputs are still inputs) don't drastically change.
  • Repair history is available from previous executions; first-time failures on new elements have lower confidence.
  • QA engineers will review and approve repairs in a timely manner; approval workflow won't bottleneck automation.
  • Screenshots of test pages can be securely stored and analyzed without exposing sensitive data.
  • Computer vision models can generalize across different apps and UI frameworks.

Constraints

  • Accuracy Trade-Off: High confidence repairs (>95%) may miss edge cases; must be balanced against false-positive risk.
  • Fintech Compliance: Page screenshots must be sanitised (mask payment data, PII); storage must be encrypted and retention limited.
  • Dynamic Content: Tests with dynamically-generated IDs or content (React keys, timestamps) cannot be healed reliably; require stable semantic anchors.
  • Multi-Browser Support: Selectors may differ across browsers (Safari vs Chrome); healing strategy must account for browser variations.
  • Mobile-Specific Challenges: Responsive layout changes may require device-specific selectors; healing must support adaptive locators.
  • Performance Budget: Healing latency must not exceed 3 seconds; real-time computer vision analysis is constrained by available CPU.

Out of Scope (v1.0)

Automatic refactoring of entire test suites to use "best practice" selectors (proactive optimization planned for v1.1).
Support for JavaScript frameworks with heavy client-side rendering (React, Vue) that render IDs dynamically – requires stable data-testid attributes.
Healing of shadow DOM elements or iframes (complex scoping; v1.1 planned).
Multi-language page support; v1 targets English-language UIs only.
Integration with visual regression tools (separate from selector healing; considered out of scope).
Proactive selector recommendations before deployment (post-deployment healing only in v1).
