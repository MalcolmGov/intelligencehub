1. Problem Statement

African fintech platforms face unprecedented fraud threats: social engineering attacks targeting customer support teams, account takeover via credential stuffing and SIM swaps, and sophisticated payment fraud schemes exploiting underinvestment in real-time fraud detection infrastructure. Traditional rule-based fraud detection systems fail to adapt to evolving attack vectors and produce unacceptable false positive rates (10–15%), driving customers to competitors.

Core Pain Points:

  • Attack Volume: 2–5% of transactions flagged as suspicious; manual review consumes 40+ hours/week from 3–4 analysts
  • Detection Lag: Fraud detected in post-transaction analysis (24–48 hours); real-time blocking limited to crude velocity checks
  • False Positives: 12–15% of legitimate transactions blocked, driving customer complaints and churn
  • Ring Fraud: Coordinated fraud rings (friends/family schemes, mule networks) escape velocity-based detection
  • Regulatory Risk: FICA (SA AML), POPIA (data protection), PCI-DSS compliance gaps create audit findings and regulatory penalties
  • Operational Overhead: Case investigation manual and unstructured; fraud intelligence not shared across teams
  • Latency Pressure: Real-time decisions required at payment (sub-50ms decision window); legacy systems take 200–500ms
Why This Matters: Fraud losses for a mid-sized fintech (~$50M annualized transaction volume) run 0.3–0.8% of volume, or $150K–$400K/year. A 60% reduction in fraud via real-time detection, combined with 50% reduction in false positives, saves $200K+/year while significantly improving customer trust and regulatory posture.

2. Current State (75% Built)

✓ Delivered Components

Real-Time Kafka Pipeline: High-throughput transaction streaming with <100ms end-to-end latency. Processes 5,000+ TPS peak load; supports backpressure and circuit breaker patterns.
26-Rule Scoring Engine: Rules across 6 categories:
  • Velocity Rules (8): Transaction count (1m, 5m, 1h, 24h windows), amount velocity, new device velocity
  • Device Rules (4): Device binding, device switching, new device in new location, jailbroken/rooted device detection
  • Geolocation Rules (3): Impossible travel (transactions >1000km in <1h), country mismatch, high-risk jurisdiction
  • Behavioral Rules (5): Transaction pattern deviation, time-of-day anomaly, merchant category anomaly, cash-out spike, KYC mismatch
  • Network Rules (3): Shared email address, shared phone number, shared device across accounts
  • Account Rules (3): Account age, profile completeness, email/phone verification status
Neo4j Fraud Ring Detector: Graph-based detection identifying coordinated fraud rings via relationship patterns (shared devices, emails, IP addresses, phone numbers, beneficial owners). Real-time ring scoring with configurable thresholds.
Device Binding Service: Hardware fingerprinting (device type, OS version, app version, device timezone, app locale) to detect account takeover via SIM swap or credential compromise. Cryptographic binding of device-account pairs with grace period for legitimate device changes.
React Analyst Dashboard: Real-time fraud alerts, case management (triage, investigation, disposition), historical fraud analysis, customer whitelist/blacklist, rule tuning interface. Supports 100+ concurrent analysts.
Compliance Framework: POPIA (South Africa data residency), PCI-DSS Level 1, FICA AML integration, DPA documentation, audit logging (all fraud decisions logged immutably).
Signal API (TypeScript): REST API for ingesting fraud signals from external systems (partner fintech, payment processors). Extensible for custom signal types.

5. Functional Requirements

FR-01: System must ingest transactions from Kafka topics at >10,000 TPS with <100ms end-to-end latency, supporting backpressure and circuit breaker patterns.
FR-02: System must apply 26-rule scoring engine (velocity, device, geo, behavioral, network, account) and compute aggregated fraud risk score in <50ms p99 latency.
FR-03: System must detect fraud rings via Neo4j graph queries (shared devices, emails, phone numbers, beneficial owners) in <200ms p99 latency.
FR-04: System must bind accounts to devices via cryptographic device fingerprinting and flag account takeover attempts (device mismatch with grace period).
FR-05: System must train and deploy XGBoost fraud classifier (AUC >0.92) and Isolation Forest anomaly detector with automated monthly retraining.
FR-06: System must perform real-time sanctions checking against OFAC SDN and FSCA PEP lists with fuzzy name matching and weekly list updates.
FR-07: System must generate SHAP explanations for each fraud decision showing feature attribution (which rules/models contributed to risk score).
FR-08: System must immutably log all fraud decisions with timestamps, rule/model output, analyst actions (approve/decline/review), and rationale.
FR-09: System must present real-time fraud alerts to analysts via dashboard, sortable by risk score, rule fired, merchant, amount.
FR-10: System must support analyst case management: triage (risk level), investigation (case notes, rule detail, ring visualization), disposition (approve/decline/refer).
FR-11: System must allow analysts to create whitelists (customer-level, transaction-level) to suppress false positives and bulk-whitelist high-value segments.
FR-12: System must support A/B testing framework for ML models: gradual rollout (10% → 50% → 100% traffic), performance comparison, automatic fallback if degradation detected.
FR-13: System must compute anomaly scores via z-score, Isolation Forest, and LOF algorithms, with ensemble scoring and calibrated thresholds.
FR-14: System must expose REST API for external fraud signal ingestion (partner fintech, payment processors) with rate limiting and authentication.
FR-15: System must support rule tuning: analysts can adjust rule weights, thresholds, and enable/disable rules via dashboard with audit trail.
FR-16: System must integrate with Kafka topics for account enrichment (user.kyc_updated, account.closed) to refresh fraud risk context in real-time.
FR-17: System must generate compliance artifacts: rule audit trail, model card (architecture, training data, fairness metrics), DPA documentation, evidence exports for audit response.
FR-18: System must visualize fraud ring topology: nodes (accounts, devices, emails, phone numbers), edges (shared attributes), ring risk score, member transaction history.

6. Non-Functional Requirements

NFR-01: Performance (Critical): <50ms p99 latency for fraud decision at 10,000 TPS; <100ms p99 for Kafka ingestion; <200ms p99 for ring detection. Dashboard <2s page load.
NFR-02: Availability: 99.9% uptime SLA with automated failover, circuit breakers, graceful degradation (fail open on latency spike; default to moderate-risk score).
NFR-03: Security: AES-256 encryption for transaction data at rest; TLS 1.3 for data in transit; API authentication via OAuth2 and API keys; role-based access control (analyst, engineer, compliance officer).
NFR-04: Data Privacy (Regulatory): POPIA compliance: data residency in South Africa (no EU transfer); right to deletion; audit logging; user consent for device fingerprinting.
NFR-05: Compliance: PCI-DSS Level 1: encryption, access control, audit logging, quarterly penetration testing. FICA AML: sanctions checking, transaction monitoring, CTR reporting.
NFR-06: Scalability: Auto-scaling Kafka consumers to handle 3x peak load (30,000 TPS); Neo4j cluster with replication for 10M+ nodes; ML model serving via load-balanced inference endpoints.
NFR-07: Reliability: Automated backup of fraud decisions, audit logs, rule config daily; RPO <1h, RTO <4h. Message deduplication in Kafka (exactly-once semantics).
NFR-08: Model Governance: Model versioning via MLflow; model card documentation (training data, fairness metrics, known limitations); bias testing (disparate impact, fairness for protected attributes). Monthly retraining validation.
NFR-09: Monitoring: Real-time alerts on latency >100ms, error rate >0.1%, fraud decision explainability (SHAP) availability, fraud loss trend (if >2σ from baseline).
NFR-10: Cost Efficiency: Target <$0.001 per transaction scored (including ML inference, Kafka, storage). Use cost-optimized model serving (quantization, distillation) without sacrificing accuracy.

7. Acceptance Criteria

Core Story: Real-Time Fraud Flagging (US-01)

Given a transaction arrives at 5,000 TPS baseline and includes amount, merchant, customer, device, geolocation
When system processes transaction
Then fraud risk score is computed and decision (approve/challenge/decline) returned in <50ms p99
And risk score breakdown shows which rules fired (velocity: 8/10, device mismatch: 3/10, geo anomaly: 2/10)
And analyst receives alert in dashboard within 1 second

Core Story: Fraud Ring Detection (US-03)

Given 5 accounts sharing a device and email address (mule network)
When one account's transaction is flagged
Then system detects ring membership, shows all 5 accounts as connected nodes, shared attributes highlighted
And all 5 accounts get elevated risk score for ring participation
And analyst can visualize ring topology in <500ms

ML Model Story: A/B Testing & Deployment (US-02)

Given new XGBoost model trained on 12M transactions with AUC 0.93 (vs. baseline 0.91)
When engineer initiates deployment
Then system routes 10% of traffic to new model for 6 hours
And if false positive rate stays within 2% of baseline, automatically promote to 50%, then 100%
And if FP rate exceeds 3%, auto-rollback to previous model
And all decisions (model version, metrics, rollback events) logged immutably

Compliance Story: Sanctions Checking & Audit Trail (US-05)

Given transaction from customer whose name matches OFAC SDN list variant
When system performs sanctions check
Then transaction is blocked immediately
And audit log records: timestamp, customer name, matched list, confidence score (name distance), analyst decision
And compliance officer can export all sanctions checks from past 30 days as CSV for regulatory proof

9. Assumptions & Constraints

Assumptions

  • 12+ months of labeled historical transaction data (fraud/legitimate) available for model training (30M+ transactions, 500K+ fraud cases)
  • Kafka infrastructure (topics, consumer groups) already in place and stable
  • Neo4j cluster operational and capable of handling 10M+ nodes with <200ms query latency
  • Core banking systems provide enrichment data (KYC, account details) via Kafka in near-real-time
  • Analysts are available 24/7 for case review; not targeting 100% automated approval
  • Business is willing to accept 3–5% false positive rate (legitimate transactions blocked) as cost of fraud prevention
  • Regulatory environment (POPIA, FICA, PCI-DSS) requirements stable through v1.0 launch

Constraints

  • Latency Budget: <50ms decision time leaves only 30–40ms for ML inference; may require model quantization or distillation
  • Data Residency (POPIA): All customer data must remain in South Africa; no EU/US transfer limits cloud provider options
  • Model Bias Risk: Historical fraud labels may be biased (e.g., certain demographics over-flagged); requires fairness testing before deployment
  • Ring Detection Scalability: Neo4j graph grows continuously; may need sharding strategy for 100M+ nodes (v2+)
  • False Positive Cost: Each blocked legitimate transaction generates customer support ticket (~$50 cost); FP rate impacts economics
  • Integration Complexity: 26-rule scoring engine tightly coupled to core banking; refactoring in critical path
  • Analyst Capacity: 200+ alerts/day with 3 analysts = 67 alerts/person/day; system must support prioritization and batching

10. Out of Scope (v1.0)

  • Behavioral biometrics (keystroke, swipe dynamics) — deferred to v2
  • Device binding on non-mobile platforms (desktop, tablet) — v1 mobile-only
  • Graph-based link prediction (predicting future fraud connections) — deferred to v2
  • Integration with third-party fraud data suppliers (LexisNexis, Threatmetrix) — v2
  • Automated decision execution (auto-approve, auto-decline) — v1 is analyst-assisted only
  • Multi-currency and cross-border transaction support — v1 South Africa ZAR only
  • Real-time retraining (continuous learning on analyst feedback) — batch monthly retraining only in v1
  • Mobile app (web-responsive dashboard only)
  • Integration with criminal justice agencies (SAPS, NPA) — regulatory, not technical scope
  • Automated fraud victim notification and recovery workflows — deferred to v2
