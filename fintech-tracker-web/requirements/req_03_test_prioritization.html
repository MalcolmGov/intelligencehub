Problem Statement

Teams run the entire test suite for every commit, regardless of code changes. This approach:

  • Wastes Time: Running 30-minute test suites when a 5-line change needs only 5 tests
  • Increases Cost: Unnecessary CI resource consumption, infrastructure waste
  • Delays Feedback: Developers wait hours for results on low-risk changes
  • Lacks Intelligence: No correlation between code changes, risk, and test relevance
  • Ignores History: Tests that previously caught defects are weighted equally with new tests

Why It Matters: Intelligent test prioritization cuts CI time by 40%+ while detecting 95%+ of defects, enabling faster iteration cycles and reducing infrastructure costs significantly.

Functional Requirements

FR-01: Code Change Analysis System shall analyze code diffs (Git) to identify modified files, functions, and modules. Extract dependency trees (call graph) to determine impacted code paths. Feed this into test selection algorithm.
FR-02: Test Coverage Mapping System shall maintain test-to-code coverage mapping at function/module level. Update mapping incrementally as coverage data changes. Enable efficient test selection based on code change impact.
FR-03: Defect Density Scoring System shall compute defect density per test based on historical data: bugs caught, false positives, failure rate. Prioritize tests with high bug-catching rate. Validate using SentinelQA's defect_risk.py.
FR-04: Risk Assessment Engine System shall compute risk score per code change combining: defect density in modified modules, code churn magnitude, business criticality (configurable), and change type (e.g., refactor vs. feature).
FR-05: Test Selection Algorithm System shall implement deterministic algorithm selecting minimal test subset covering modified code with high confidence. Guarantee execution of high-risk tests. Allow manual override (run full suite).
FR-06: Runtime Execution Engine System shall wire defect_risk.py scoring into live test runner (Jenkins, GitHub Actions, etc.). Execute prioritized test order. Provide real-time progress and early feedback on failures.
FR-07: CI/CD Integration Hooks System shall expose webhooks/plugins for GitHub, GitLab, Jenkins integration. Accept code change events, trigger prioritization, return test selection results to CI/CD pipeline. Support push and pull request contexts.
FR-08: Business Rules Engine System shall allow QA teams to define rules (e.g., "always run tests in payment module"). Override algorithm recommendations when criticality demands full suite. Audit rule overrides.
FR-09: Results Dashboard System shall display test execution summary: tests selected, execution time, results, code coverage achieved. Show comparison: selected subset vs. full suite (if run). Highlight time/cost savings.
FR-10: A/B Testing Mode System shall support experimental mode: run prioritized tests + full suite in parallel. Compare results. Report false negatives (tests skipped that would have failed in full suite).
FR-11: Parallel Test Execution System shall intelligently batch independent tests for parallel execution. Estimate end-to-end time given test dependency graph. Balance parallelism vs. resource constraints.
FR-12: Historical Analytics System shall maintain time-series database of: test effectiveness (bugs caught), execution times, failure rates, code churn trends. Enable retroactive analysis of prioritization accuracy.
FR-13: Notifications & Alerts System shall notify developers of test results, time savings, and high-risk changes detected. Support Slack, email, webhook integrations. Alert on false negatives or algorithm anomalies.
FR-14: API for Test Selection System shall expose REST API: POST code diff -> GET prioritized test list + risk assessment. Enable programmatic integration with custom CI/CD systems.
FR-15: Performance Tracking System shall track and report: average time savings per PR, infrastructure cost reduction, defect detection rate vs. full suite. Export metrics for business dashboards.

Non-Functional Requirements

Performance

Code change analysis + test selection in <30 seconds. API response time <500ms p95. Support 10k+ test repositories. Parallel test execution without bottlenecks.

Scalability

Handle 1000+ concurrent code analysis requests. Support organizations with 500+ repositories. Process 100M+ test executions/day for analytics. Scale test selection algorithm linearly.

Reliability

99.5% uptime SLA. Graceful fallback to full suite if prioritization fails. Deterministic algorithm (reproducible results). Fail-safe defaults ensure critical tests never skipped.

Security

Encrypt code diff data in transit (TLS) and at rest. RBAC for business rules configuration. Audit log all rule changes. Sanitize code diffs before storage.

Observability

Export prioritization metrics (Prometheus). Debug logs for algorithm decisions (feature weights). Alert on anomalies (unusual time savings, false negatives spike).

Usability

Dashboard shows clear rationale for test selection. Mobile-responsive UI. Dark theme. API documentation with code examples. Wizard for CI/CD integration.

Acceptance Criteria

AC-1: Test Selection Accuracy

Given 50 code changes with known defect outcomes, When prioritization algorithm runs, Then selected test subsets catch >95% of bugs found by full suite, with <50% average time reduction.

AC-2: Risk Assessment Correctness

Given a high-risk code change (payment module), When risk scoring runs, Then risk score >70 (out of 100) and all payment-related tests are included in selection.

AC-3: CI/CD Integration

Given a GitHub pull request, When webhook fires, Then system returns test selection result within 30 seconds. GitHub Actions job receives result and executes selected tests only.

AC-4: Execution Performance

Given 1000 test cases analyzed for code change, When algorithm runs, Then test selection (50-200 tests) completes in <30 seconds with average 40%+ time reduction vs. full suite.

AC-5: False Negative Reporting

Given A/B test mode enabled, When prioritized and full suites run in parallel, Then system detects and alerts if any test skipped would have failed (false negative). Rate <5%.

AC-6: Business Rules Override

Given payment module rule ("always run payment tests"), When non-payment code changes, Then payment tests are still included in selection. Audit log captures rule application.

Dependencies & Integrations

  • SentinelQA defect_risk.py: Advisory mode stub. Must be expanded to runtime execution engine.
  • CI/CD Systems: Jenkins, GitHub Actions, GitLab CI. Webhook integration required.
  • VCS Integration: Git API for code diff analysis and dependency graph extraction.
  • Test Coverage Tools: Istanbul, Cobertura, pytest-cov for test-to-code mapping.
  • Data Storage: PostgreSQL or ClickHouse for historical analytics. Redis for caching test metadata.
  • Notification Platforms: Slack, email, PagerDuty for alerts and results.
  • Container Orchestration: Docker, Kubernetes for parallel test execution infrastructure.
8

Assumptions & Constraints

  • Code diffs are accessible via Git API. Teams use feature branch workflows (not trunk-based).
  • Test coverage data is available and regularly updated.
  • Historical test execution results are available (minimum 6 months recommended for accurate defect density).
  • Organizations trust AI-driven test selection (v1 may have >5% false negatives; iterative refinement needed).
  • Constraint: v1 targets functional/unit tests. Contract and E2E tests deferred to v2.
  • Constraint: Maximum 10k test cases per analysis. Larger suites require v2 optimization.
  • CI/CD systems must support dynamic test list specification (most modern systems do).
