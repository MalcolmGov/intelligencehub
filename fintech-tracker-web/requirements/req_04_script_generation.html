Problem Statement

Converting test cases into runnable automation scripts requires specialized knowledge of each testing framework (Playwright, Cypress, Jest, Pytest), boilerplate code structure, and best practices for selectors, assertions, and error handling. QA engineers frequently:

  • Spend 60–80% of automation time writing boilerplate setup, teardown, and helper functions
  • Struggle with framework-specific syntax, leading to slow script development and inconsistent patterns
  • Duplicate fixture logic and assertion patterns across test files
  • Cannot quickly switch between frameworks when projects require different tech stacks
  • Face delays when learning new frameworks, blocking feature testing

For SentinelQA, enabling rapid, framework-agnostic test script generation unlocks faster automation cycles, reduces ramp-up time for new team members, and allows QA to focus on test logic rather than boilerplate engineering.

Target Users & Personas

1. Jordan Lee – Mid-Level Automation Engineer
Role: Writes and maintains Playwright/Cypress scripts
Goals: Convert test cases to runnable scripts in <15 minutes, reduce context-switching between frameworks, maintain code consistency
Frustrations: Spends hours writing boilerplate; forgot Cypress syntax when switching projects; inconsistent CSS selector patterns
2. Alex Rodriguez – Senior SDET (Senior Development Engineer in Test)
Role: Owns test framework architecture and CI/CD integration
Goals: Standardize script generation across projects, enforce coding standards, reduce tech debt from inconsistent scripts
Frustrations: Too many script style variations; difficult to maintain; new team members write inefficient code
3. Lisa Zhang – QA Engineer with Python Background
Role: Primarily writes Pytest scripts, occasionally needs JavaScript (Playwright)
Goals: Generate JavaScript/Playwright scripts without learning syntax, reuse Python-based fixtures in JavaScript, fast ramp-up
Frustrations: Doesn't know JavaScript well; typing errors; copy-paste frustration; can't quickly contribute to Playwright tests
4. CTO/Engineering Lead – Multi-Framework Fintech Org
Role: Sets testing standards across backend (Pytest), API (Playwright), and UI (Cypress) teams
Goals: Ensure consistent test quality across frameworks, reduce onboarding friction, speed up test coverage
Frustrations: Different teams write tests differently; hard to enforce best practices; slow to scale QA

Must Have
US-11
As an SDET, I want generated scripts to follow a project-specific coding standard (custom naming conventions, assertion library, fixture patterns), so that all auto-generated scripts maintain consistent quality and are mergeable without linting failures.
Must Have

As a QA engineer, I want generated Playwright/Cypress scripts to include smart element selectors (robust CSS/XPath, data attributes, ARIA labels), so that tests are resilient to minor UI changes and don't fail on layout updates.

As a QA engineer, I want to push generated scripts to GitHub as draft PRs (like test cases), review them, and merge them into the test suite without manual file creation, so that the automation pipeline is streamlined end-to-end.

Functional Requirements

FR-16Accept test steps in plain English and generate syntactically-correct, runnable scripts in Playwright, Cypress, Jest, or Pytest based on user selection.
FR-17Generate element selectors using a priority strategy: data attributes > ARIA attributes > CSS ID > robust CSS classes > XPath; fall back to computer vision if no selectors found.
FR-18Support project-level configuration: custom naming conventions, assertion library (Chai, Jest Matchers, pytest assertions), base URLs, timeouts, retry policies.
FR-19Generate parameterised tests that accept CSV/JSON fixture files and loop over test data; output proper test naming per iteration (e.g., test_login[user1], test_login[user2]).
FR-20Detect common patterns in test steps and auto-generate reusable page objects / helper functions with proper documentation.
FR-21Include error handling, timeout configuration, retry logic, and failure screenshots/videos in generated scripts.
FR-22Generate API test scripts (Pytest requests, Jest supertest) with proper authentication, header/body validation, and schema checking.
FR-23Support batch script generation: convert 50+ test cases to scripts in one async job with progress tracking and email notification.
FR-24Create GitHub draft PRs with generated scripts, allowing review, edit, and merge into feature/main branch.
FR-25Allow engineers to edit generated scripts, mark as approved/rejected, and use feedback to refine generation for future scripts.
FR-26Export scripts with proper file structure: organized folders per feature, shared fixtures in common/ folder, CI config templates.
FR-27Validate generated scripts for syntax errors and test-ability (can be parsed and dry-run without execution) before PR creation.

Non-Functional Requirements

NFR-09Performance: Generate 10 scripts from test cases in <5 seconds; support batch conversion of 100 scripts in <60 seconds (async).
NFR-10Code Quality: Generated scripts must pass linting (ESLint for JS, pylint for Python) and adhere to code style standards without manual fixes.
NFR-11Consistency: All generated scripts for a project follow identical patterns; fixture reuse across scripts is automatic; no boilerplate duplication.
NFR-12Extensibility: Support for custom fixtures and helper functions defined in project templates; framework-agnostic generation logic.
NFR-13Security: Sanitise sensitive data in scripts (no hardcoded passwords, API keys, or PII); support secret injection via environment variables.
NFR-14Maintainability: Generated scripts include comments explaining steps, selectors, and assertions for future maintenance.
NFR-15Auditability: Log all script generation with framework version, AI model version, project config, and output checksum for reproducibility.

Acceptance Criteria

Feature: Test Case → Script Generation

Given a test case with steps (e.g., "Click Login button, Enter email, Click Submit"), when selected for Playwright generation, then a syntactically-valid Playwright script is produced with correct selectors, locators, and assertions within 5 seconds.
Given a test case and Pytest selected, when converted, then a properly-structured Pytest file is generated with fixtures, setup/teardown, and assert statements matching team conventions.
Given a generated script, when linted with ESLint (JS) or pylint (Python), then zero linting errors are reported without manual edits.

Feature: Parameterised Test Generation

Given a test case and a CSV with 5 user rows, when converted to Playwright, then 5 separate test variations are generated with proper naming (test_login[row1], test_login[row2], etc.).
Given parameterised Pytest, when run, then all parameter combinations execute and report independently.

Feature: GitHub PR Creation

Given 20 generated scripts, when "Create PR" is selected, then a single draft PR is created with all scripts in organized folder structure and a clear commit message.
Given a generated script in a PR, when viewed on GitHub, then it includes comments explaining test purpose and key assertions.

Feature: Project Configuration Compliance

Given a project config with custom assertion style and timeout settings, when scripts are generated, then all scripts use the specified style without exceptions.

Assumptions & Constraints

Assumptions

  • Test cases are structured with clear steps; vague or ambiguous steps will produce lower-quality scripts.
  • Project configurations (naming conventions, assertion styles) are defined upfront by SDETs.
  • Generated scripts will be reviewed and refined by engineers; AI output is a starting point.
  • Element selectors are stable and can be identified from UI screenshots or provided in test case metadata.
  • Engineers have basic familiarity with the generated framework (no starter course required).

Constraints

  • Framework Coverage: v1 supports Playwright, Cypress, Jest, Pytest only; other frameworks (Selenium, TestCafe) not supported in v1.
  • Selector Robustness: AI-generated selectors may fail on significant UI redesigns; manual adjustment required for complex dynamic elements.
  • Custom Fixtures: If project uses proprietary fixture patterns, custom templates must be provided upfront.
  • API Rate Limits: GitHub API rate limiting applies to batch PR creation; queue management required for 100+ scripts.
  • Secret Management: Generated scripts must not include hardcoded credentials; environment variable injection required for local testing.

Out of Scope (v1.0)

Test execution or result reporting (handled by CI/CD pipelines).
Mobile app automation (Appium, XCUITest) – web-only in v1.
Visual regression testing or computer vision-based selectors (fallback only, not primary).
Automatic migration of existing manual scripts to AI-generated format.
Support for languages beyond English for test case input.
Integration with ALM/test management tools beyond GitHub (Jira, Azure DevOps plugins planned for v1.1).
Code review automation or approval workflows (manual QA review required).
