1. Executive Summary & Business Case

Mobile money fraud in sub-Saharan Africa is dominated by account takeover and SIM swap attacks, where an attacker gains access to a victim's device or phone number and executes transactions before the customer can respond. Once a session is established and the attacker passes the PIN authentication screen, existing security controls are essentially blind. PIN authentication is a point-in-time check; it cannot detect if the person using the app after authentication is the legitimate account holder or an attacker who has taken control mid-session.

UC-32 introduces a fundamentally different security paradigm: continuous, invisible, passive authentication throughout the entire session. The on-device ML model learns each user's unique behavioural fingerprint from 47 distinct signals — the precise pressure of their swipe, their characteristic typing cadence between PIN digits, the angle at which they hold their phone, the rhythm of their tap-to-confirm patterns — and continuously scores the probability that the current user matches the enrolled profile. A session takeover by an attacker who does not share these behaviours is detected within 30–60 seconds, triggering a step-up authentication challenge.

The system is architecturally private-by-design: the behavioural model lives entirely on the user's device. Raw sensor data is never transmitted. Federated learning allows model improvements to be aggregated across users without raw data leaving any device. The user experiences zero friction until a risk threshold is breached. This combination of invisible protection and privacy-preserving architecture makes UC-32 a genuinely novel security capability that directly addresses the most damaging fraud vector in MTN's Mobile Money portfolio.

2. Problem Statement

Problem 1 — PIN Authentication Cannot Detect Session Takeover
MTN MoMo's current authentication model is PIN-only at session initiation. Once a session is active, there is no ongoing verification that the authenticated user is still the person in control of the device. Account takeover fraud typically occurs mid-session: the attacker compels the victim to open the app and enter their PIN under social engineering pressure, then physically takes the device. From the system's perspective, this is an authenticated, legitimate session. The fraud is invisible to all existing controls.
Problem 2 — SIM Swap Fraud Bypasses All Device Controls
SIM swap fraud — where an attacker fraudulently transfers a victim's phone number to a new SIM — allows the attacker to receive all OTPs and authentication messages. In markets where OTP-based auth is used as a second factor, SIM swap entirely neutralises this control. South Africa alone reported over 2,400 SIM swap fraud incidents in 2025 targeting mobile money accounts. UC-32's behavioural biometrics detect the attacker's different behavioural fingerprint on a cloned session regardless of SIM ownership.
Problem 3 — Friction-Based Security Drives Customer Abandonment
Existing fraud countermeasures — transaction delays, secondary PIN prompts, OTP challenges on every transaction — create friction that drives customers away from the app and back to the less secure USSD channel or to competitor platforms with weaker but faster security. UC-32 resolves this dilemma: security is invisible to the legitimate user (no extra steps) and only triggers challenge authentication when the behavioural anomaly score exceeds a risk threshold, targeting zero false-positive impact on the legitimate user experience.

4. User Stories & Acceptance Criteria

US-32-01
Silent Fraud Prevention — Session Takeover
"As Grace, a MoMo app user who has been compelled to unlock my phone and hand it to an attacker, I want the app to detect that someone else is using it and block the transaction before money leaves my account, without me having to do anything."
Acceptance Criteria
  • Behavioural score drops below threshold within 60 seconds of a different person using the device
  • High-value transaction (above market-defined threshold) is blocked and step-up auth triggered
  • Step-up challenge is delivered silently as if normal app flow (no "fraud detected" message shown to attacker)
  • Legitimate user notified by push notification that a challenge was triggered
  • If challenge fails, session terminated and account temporarily locked
US-32-02
Zero-Friction Legitimate User Experience
"As a regular MoMo app user, I want to use the app exactly as I always have without any extra steps, prompts, or delays caused by the fraud protection layer, so that security does not create friction that makes me prefer the USSD channel."
Acceptance Criteria
  • SDK data collection adds <5ms to UI interaction latency
  • False positive rate <0.1% (legitimate users should not see step-up challenge more than once per 1,000 sessions)
  • No visible security UI element during normal operation
  • App launch time not increased by more than 200ms by SDK initialisation
  • Battery drain attributable to SDK <0.5% per 10-minute session
US-32-03
Behavioural Model Enrolment
"As a new MoMo app user, I want my behavioural profile to build passively over my first few sessions without me needing to do anything, so that I gain fraud protection automatically without a burdensome onboarding process."
Acceptance Criteria
  • Model enters active monitoring mode after 5 minutes of cumulative app interaction (across sessions)
  • No explicit enrolment action required from user
  • Model confidence score shown in security settings for technically curious users
  • User can opt out of behavioural monitoring in privacy settings at any time
  • Opting out immediately destroys all on-device behavioural model data
US-32-04
Graceful Handling of Legitimate Behavioural Change
"As a MoMo user who has injured my hand, I want the system to adapt to my changed interaction patterns within a few sessions rather than repeatedly challenging me, so that temporary behavioural changes don't create security friction for weeks."
Acceptance Criteria
  • Model updates continuously with each confirmed-legitimate session
  • After 3 successful step-up challenges in 7 days, model sensitivity is temporarily reduced and retraining prioritised
  • Retraining convergence to new behavioural baseline within 5–10 sessions
  • User can manually trigger model reset via security settings to accelerate re-enrolment
US-32-05
Privacy-Preserving Architecture — Compliance Officer
"As a Group Data Protection Officer, I want to confirm that no raw behavioural data leaves the user's device, so that UC-32 can be deployed across all markets without triggering cross-border data transfer restrictions under POPIA and NDPR."
Acceptance Criteria
  • Architecture review confirms raw sensor data (touch coordinates, pressure, accelerometer) never transmitted to any server
  • Only model weight gradients (anonymised) transmitted for federated learning aggregation
  • Differential privacy guarantees applied to federated gradients (ε ≤ 5)
  • Third-party security audit confirms no data leakage via SDK
  • POPIA data minimisation documentation produced for Group DPO sign-off
US-32-06
Risk Threshold Configuration — Security Operations
"As a Security Operations analyst, I want to configure the behavioural anomaly threshold per market and transaction type, so that I can tune the sensitivity to match local fraud patterns without redeploying the SDK."
Acceptance Criteria
  • Risk threshold configurable per: market, transaction type, transaction amount band
  • Threshold changes take effect in SDK within 24 hours via remote config (no app store update)
  • Real-time dashboard shows: anomaly score distribution, step-up rate, fraud catch rate by threshold
  • A/B threshold testing supported with cohort assignment via server-side flag

7. Data & AI Model Requirements

On-Device Personal Model Architecture
Lightweight autoencoder (encoder: 47 signals → 16-dim embedding; decoder: 16-dim → 47 signals). Reconstruction error used as anomaly score. Model size target: <5MB for iOS CoreML / TFLite. Enrolment: 5 minutes cumulative interaction. Continuous incremental update on confirmed legitimate sessions using federated learning local round. Quantised to INT8 for inference efficiency.
Global Base Model (Federated)
Federated average of local model weights from opted-in devices, updated weekly. Provides starting point for new users to reduce cold-start time from 5 minutes to approximately 2 minutes. Protected by differential privacy (Gaussian mechanism). Separate market-level base models to account for regional device type and interaction pattern differences.
Signal Weighting
Not all 47 signals are equally discriminative across all users and devices. The model learns per-user signal weights during enrolment. Signals with low discriminative power for a given user (e.g., pressure on devices without pressure sensors) are automatically down-weighted. This ensures the model remains robust across the diverse Android device ecosystem prevalent in MTN markets.

8. Compliance & Regulatory

POPIA — Behavioural Data as Personal Information
Behavioural interaction data (touch patterns, typing cadence) constitutes "personal information" under POPIA as it relates to and is collected from an identifiable natural person. The privacy-by-design architecture (on-device processing, no raw data egress) significantly reduces but does not eliminate POPIA obligations. Consent is required for: (1) collection and processing of behavioural data for authentication purposes; (2) federated learning gradient sharing. Consent must be explicit, informed, and withdrawable. The on-device nature enables a compelling data minimisation argument to regulators.
POPIA Section 72 — Information Officer Obligations
MTN's Information Officer must include the behavioural biometric system in the PAIA/POPIA manual and record of processing activities. The system must be assessed in a DPIA given the automated profiling of all active MoMo app users. The DPIA must document: the categories of data processed, on-device processing architecture, retention periods (effectively zero on server side), and the step-up authentication decision logic.
NDPR — Nigeria Biometric Processing
NDPR classifies behavioural patterns used for identification as sensitive personal data requiring explicit consent. The behavioural biometric framework must be registered with NITDA before deployment in Nigeria. The NDPR audit trail requirement means that even on-device processing events (step-up triggers, authentication outcomes) must be logged in a format accessible for regulatory inspection.

9. Sprint Plan & Roadmap

Sprint 1 (Weeks 1–3): SDK Foundation & Signal Collection

Sprint 1 Deliverables
  • iOS Swift SDK: 47-signal collector (UITouch, CMMotionManager, UIKeyInput events), feature extractor, local storage (encrypted)
  • Android Kotlin SDK: 47-signal collector (MotionEvent, SensorManager, InputMethodManager), feature extractor, local storage (Android Keystore)
  • CoreML and TFLite autoencoder model: architecture design, training on synthetic behavioural dataset, quantisation
  • MoMo app SDK integration hooks: session start/end events, transaction intercept API
  • POPIA consent capture: opt-out mechanism in privacy settings with immediate model destruction
  • Battery and latency benchmarking on Samsung Galaxy A22 (Africa target device)

Sprint 2 (Weeks 4–6): Anomaly Scoring, Step-Up & Federated Learning

Sprint 2 Deliverables
  • Anomaly scoring engine: continuous score (0–1), 5-second update cycle, threshold comparison
  • Step-up authentication integration: silent trigger, challenge UI, PIN/biometric options
  • Account lock mechanism: 3-failure lockout, push notification to legitimate user, USSD unlock fallback
  • Federated learning infrastructure: gradient aggregation server, differential privacy (Gaussian mechanism, ε=5), weekly round scheduling
  • Remote config service: per-market threshold management, A/B test flag support
  • SOC dashboard v1: anomaly score distribution, step-up rate, per-market breakdown
  • UC-16 PayGuard integration: step-up trigger events forwarded to fraud event bus

Sprint 3 (Weeks 7–9): Pilot, Red Team & Privacy Audit

Sprint 3 Deliverables
  • Pilot deployment: MTN South Africa, Nigeria (50,000 user cohort per market, opt-in)
  • Red team exercise: session takeover attack simulation, SIM swap attack simulation, replay attack
  • False positive rate measurement over 30-day pilot period
  • DPIA completed and filed with Group DPO; NITDA notification for Nigeria
  • Third-party SDK security audit (no data leakage validation)
  • Model enrolment quality metrics: median time to confident model, signal coverage by device type
  • User experience research: friction measurement, step-up complaint rate
  • Full market rollout plan with per-market threshold recommendations
