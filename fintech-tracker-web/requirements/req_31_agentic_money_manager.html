1. Executive Summary & Business Case

MTN MoMo has onboarded over 65 million subscribers across 13 markets, but a significant proportion of these accounts sit dormant — customers who registered for Mobile Money but do not actively transact. Industry research pegs wallet dormancy rates across African mobile money platforms at 35–55%, representing a direct revenue loss and a customer engagement failure. The current MoMo product is a reactive tool: it waits for the customer to initiate every action. This interaction model fails customers whose financial lives require consistent, automated management that they do not have the time, cognitive bandwidth, or financial literacy to execute manually.

UC-31 transforms MoMo from a passive payment rail into an autonomous financial agent. Users define financial policies — rules expressed in a plain-English policy DSL (Domain-Specific Language) — and the AI agent executes those policies automatically on their behalf. Bill payments are made the moment they're due. Savings are rounded up from every transaction and moved to a savings pocket. Investment contributions are executed on payday. The agent is not a chatbot providing suggestions; it is an actor with delegated authority to execute within user-defined constraints.

The business case is direct: a 35–45% reduction in wallet dormancy at current subscriber volumes converts dormant accounts into active transactors, generating fee revenue on each automated transaction. Engaged customers also demonstrate 2–3x higher cross-sell conversion for premium MoMo products. The agent creates a daily engagement habit — customers check their MoMo to see what the agent has done for them, dramatically increasing DAU metrics.

2. Problem Statement

Problem 1 — Manual Money Management Creates Financial Stress and Dormancy
The majority of MoMo's target customer base — informal economy workers, market traders, domestic workers — have irregular income, multiple financial obligations, and limited time to actively manage their finances. Requiring every MoMo action to be manually initiated means bills are missed, savings intentions never materialise, and the wallet sits unused between the sporadic transactions the customer remembers to initiate. Financial passivity is not laziness; it is a rational response to cognitive overload.
Problem 2 — Dormant Wallets Represent Massive Unrealised Revenue
An estimated 35–55% of MTN MoMo accounts are dormant at any given time. These accounts represent customers who have onboarded but not engaged sufficiently to derive value. Re-engaging a dormant customer is 5–7x more expensive than retaining an active one. An agent that executes transactions automatically on the customer's behalf converts dormant accounts into active transactors without requiring customer re-acquisition spend.
Problem 3 — No Trusted Autonomous Financial Management Tool for the Informal Economy
Sophisticated financial automation tools (robo-advisors, auto-savings apps, bill payment schedulers) exist in developed markets and are marketed to formally employed, banked customers. No comparable tool exists for informal economy workers in Africa who transact via mobile money. UC-31 delivers this capability to MTN's core customer base — a genuinely differentiated product that competitors without an agentic AI investment cannot replicate.

4. User Stories & Acceptance Criteria

US-31-01
Automated Bill Payment Policy
"As Thabo, a taxi driver in Johannesburg, I want to set up a rule that pays my electricity bill automatically on the 25th of every month from my MoMo wallet, so that I never face a disconnection again without having to remember to pay."
Acceptance Criteria
  • User can create a bill payment policy via natural language or structured form in the MoMo app
  • Policy is expressed as: IF date = 25th AND balance > bill amount THEN pay [biller] [amount]
  • Agent executes payment at 08:00 on the specified date
  • Push notification sent to user 24 hours before and immediately after execution
  • If balance insufficient, user is notified 48 hours before due date with shortfall amount
  • Full audit entry: policy ID, trigger condition, execution timestamp, transaction ID, balance at time of execution
US-31-02
Auto-Savings Roundup
"As Amara, a market trader, I want to automatically save the 'change' from every transaction I make, rounding up to the nearest 100 naira and moving it to my savings pocket, so that I build savings without feeling the sacrifice."
Acceptance Criteria
  • User activates roundup savings with configurable rounding unit (50, 100, 500 in local currency)
  • Agent detects every outgoing transaction and calculates roundup amount
  • Roundup moved to savings pocket within 30 seconds of triggering transaction
  • Weekly savings summary notification showing total saved via roundup
  • Roundup paused automatically if wallet balance drops below user-defined floor
  • User can withdraw from savings pocket at any time; no lock-in
US-31-03
Payday Investment Policy
"As a salaried worker, I want to automatically invest 10% of my salary payment the moment it arrives in my MoMo wallet into a MoMo Invest product, so that I invest before I spend."
Acceptance Criteria
  • Agent detects inbound salary payment via transaction label or known payer MSISDN
  • Configured percentage transferred to investment product within 5 minutes of salary receipt
  • POPIA consent obtained for agent to access incoming transaction data for trigger detection
  • Investment execution confirmation notification with amount invested and portfolio update
  • User can modify or pause the policy at any time; pending executions cancelled within 60 seconds
US-31-04
User Override & Pause Control
"As a MoMo agent user, I want to be able to pause all agent activities instantly when I'm in financial difficulty, and review every action the agent has taken, so that I remain in complete control of my money."
Acceptance Criteria
  • Single-tap "Pause Agent" control available on home screen; all scheduled actions paused within 60 seconds
  • Full audit log accessible in app: every agent action, trigger event, amount, and timestamp
  • User can reverse any agent-initiated transaction within 15 minutes if within same platform
  • Emergency pause also available via USSD *165*STOP# command
  • Paused state persists until user explicitly resumes; no automatic re-activation
US-31-05
Natural Language Policy Creation
"As a non-technical user, I want to describe my financial policy in plain English or my local language and have the agent convert it into an executable rule, so that I don't need to understand if/then logic to automate my finances."
Acceptance Criteria
  • NL policy parser accepts input in English, Swahili, Hausa, Zulu, French, and Yoruba
  • Parsed policy presented to user for confirmation in plain language before activation
  • Policy DSL representation shown as "advanced view" for technically confident users
  • Ambiguous policies prompt clarifying questions (max 2 follow-up questions)
  • Policy library of 20+ pre-built templates available as starting points
US-31-06
POPIA Consent & Delegated Authority
"As a compliance officer, I want every agent-initiated transaction to be traceable to an explicit user consent and policy, so that MTN can demonstrate regulatory compliance for autonomous financial actions."
Acceptance Criteria
  • Every agent activation requires explicit, informed consent with policy scope clearly stated
  • Consent stored with timestamp, policy ID, version, and channel (app/USSD)
  • Every autonomous transaction references the policy ID and consent event in its audit record
  • Consent withdrawal immediately deactivates all policies; in-flight transactions cancelled
  • Annual consent re-confirmation prompted for all active agent policies

7. Data & AI Model Requirements

NL-to-APL Policy Compiler
Fine-tuned instruction-following LLM (Llama 3 8B or equivalent) trained on MTN MoMo domain vocabulary and APL grammar. Input: user natural language policy description. Output: structured APL policy + plain-language confirmation text. Hosted server-side (no user data leaves platform). Inference latency <2 seconds.
Salary / Inbound Payment Detector
Transaction classification model distinguishing salary inflows from other credits, based on: amount regularity, payer MSISDN consistency, time-of-month patterns, transaction label keywords. Per-user model trained on 90-day rolling transaction history. Precision target: >95% to avoid false-positive investment triggers.
Policy Conflict Detection
Rule-based conflict detector identifying: circular dependencies between policies, double-spend risks (two policies targeting same balance), and ordering conflicts (roundup after a send that drains the wallet). Executed at policy activation time, not at runtime, to prevent mid-execution failures.

8. Compliance & Regulatory

POPIA — Autonomous Financial Action Consent
Autonomous execution of financial transactions on behalf of a data subject requires a lawful basis under POPIA Section 11. The recommended basis is explicit consent (Section 11(1)(a)) with the scope of delegated authority clearly defined. MTN must ensure: (1) consent is freely given, specific, informed, and unambiguous; (2) withdrawal is as easy as giving consent; (3) all autonomous actions are traceable to a specific consent event; (4) data subjects can access their full audit trail on request; (5) the automated decision-making transparency requirements under Section 71 are met, giving users the right to understand how agent policies are triggered.
FSCA — Automated Financial Advice
Pre-built policy templates that recommend investment or savings allocations may constitute "financial advice" under the Financial Advisory and Intermediary Services (FAIS) Act (South Africa). Legal review required to determine whether template recommendations require an FSP licence. Conservative approach: templates present options without recommendation language; user explicitly selects and configures all financial parameters.
NDPR / CBN — Nigeria Automated Transaction Rules
The CBN's e-Payment guidelines require that recurring automated debit mandates be explicitly authorised by the account holder with a clearly defined scope (maximum amount, frequency, duration). Agent bill payment policies that trigger recurring debits must comply with CBN mandate registration requirements. NDPR requires explicit consent for automated processing of personal data used in policy triggers.

9. Sprint Plan & Roadmap

Sprint 1 (Weeks 1–3): DSL Design & Core Engine

Sprint 1 Deliverables
  • APL (Agent Policy Language) formal grammar specification — triggers, conditions, actions, guards, on_fail primitives
  • Policy parser and validator implementation (ANTLR4 grammar)
  • Policy rule engine v1 (event-driven, Redis Stream): scheduled triggers and transaction event triggers
  • MoMo API delegated authority token model (OAuth 2.0 scoped tokens)
  • POPIA consent management service: consent capture, storage, withdrawal, version tracking
  • Immutable audit log schema and write API
  • Bill payment policy (scheduled trigger) end-to-end proof of concept in staging

Sprint 2 (Weeks 4–6): NL Compiler, Savings, Investment

Sprint 2 Deliverables
  • NL-to-APL policy compiler: fine-tuned LLM, APL output schema, user confirmation flow
  • Roundup savings policy: transaction event trigger, savings pocket API integration, balance guard
  • Payday investment policy: salary detector model, investment product API integration
  • Policy conflict detection engine (circular dependencies, double-spend guards)
  • 20 pre-built policy templates (English, Swahili, Hausa initial release)
  • Pause agent feature: in-app toggle, *165*STOP# USSD command, graceful in-flight cancellation
  • Push notification service: pre-execution alerts, post-execution confirmations, failure notifications
  • Agent dashboard UI in MoMo app: policy list, audit log, pause control

Sprint 3 (Weeks 7–9): Pilot, Compliance Hardening & Scale

Sprint 3 Deliverables
  • Pilot deployment: MTN South Africa (10,000 user cohort) — bill payment and roundup savings only
  • FSCA legal review of investment template compliance
  • POPIA consent audit: verify all autonomous transactions traceable to consent events
  • CBN mandate registration integration for Nigeria recurring debits
  • Policy template library expansion to 20 templates in 5 languages
  • Audit log export for data subject access requests (DSAR) automation
  • Load testing: 500K concurrent active policies, 1M trigger events per hour
  • Dormancy metric baseline and 30-day trend measurement post-pilot
